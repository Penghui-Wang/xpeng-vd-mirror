# 帧率优化记录：从 6fps 到 60fps

这份文档只讲帧率。每一步记三件事：**当时看到什么、判断是什么、改了什么、结果多少**。
包括走错的弯路 —— 有几处「看起来一定是瓶颈」的地方，实测一点用都没有。

最终状态（1920×720 仪表，550×384 投屏矩形，腾讯视频全屏播放）：

```
车机  VDS| fps=62 cap=8590 proc=8590 sent=8322 bytes/s=7917462 procMs=7
仪表  frames=7860 59.9fps (recv 550x384) read=1.08ms dec=7.10ms draw=4.15ms flush=3.46ms | total=15.8ms
```

## 1. 演进总表

| 阶段 | 关键改动 | 仪表帧率 | 瓶颈当时在哪 |
|---|---|---|---|
| 起点 | zlib + 全屏带 960×360 | 5–8 | 仪表解压（90–140ms/帧） |
| LZ4 | 换 LZ4，1920×720 完整链路 | 19.7 | 整帧 50.88ms，decode 单独就 23ms |
| DIRECT | 尺寸命中就不缩放，解压直写 | 23.5 | 42.59ms |
| 串行 | 换 `captureDisplay` 采集，链路重做，三段串行 | 20.3 | read 1.2 + dec 24.6 + fb 21.9 |
| 流水线 | 解码 goroutine + 单 worker 写 fb | 22.9 | 两核抢内存带宽 |
| 降刷新 | `ICBANDS` 250 → 1200ms | 25.8–27 | 每 5 帧白吃一帧整幅刷 |
| 矩形出帧 | 接收端按仪表实际矩形出帧 | 30.1 | **发送端 `targetFps=30`** |
| **v1.0** | 去重复落屏写、窄写、修 LZ4 补登记 | **58.6** | 采集 62fps / 发送 47fps |
| 剥离 UI | 拆掉卡片绘制与四个子命令 | **59.9** | 已贴屏上限 |

23.5 → 20.3 那一格不是退化：23.5 是 `screencap` 时代 1920×568 整带宽度的数字，
后来采集换成 `captureDisplay`、写屏也换成矩形，链路和宽度全变了，不能直接比。
真正可比的是同一路线下的 20.3 → 22.9 → 25.8 → 30.1 → 58.6。

58.6 之后剩下的时间全在 15–17ms 徘徊，而 60Hz 的预算是 16.7ms —— 到头了。

## 2. 先判断天花板在谁身上，再动手

这是整件事最重要的一条。前面几轮之所以慢，是**改了不该改的地方**。

v0.9 时仪表日志打的是 `30.1fps`，看起来像是接收端到顶了。但车机日志同时打着 `fps=30`，
`targetFps=30` 的节流产物 —— 接收端只是刚好追平，**它根本没有被压满**。
只优化接收端，一帧都涨不上去。

判断方法很朴素：**两端各看一眼自己的节流/丢弃计数，谁的计数器先到顶，谁的锅。**

- 车机看 `cap`（采集）和 `sent`（发出）：两者差越来越大 → 发送侧是瓶颈
- 仪表看 `frames=N` 除以运行秒数，和分项加总对不对得上 → 对不上是统计错，别信

v1.0 第一次跑 60fps 时就是这个判据救了场：`cap=1989 sent=1692` 差 297 帧且每 2 秒再扩大一次。
采集端跑满 62fps，发送线程只发得出去 47fps，中间全被单槽队列覆盖丢掉。
**如果只看仪表那个 47fps 去优化接收端，方向就完全错了。**

## 3. 各阶段细节

### 3.1 换 LZ4：6 → 19.7fps

上游 `instrument-projection` 实测 zlib/tinf 解压 90–140ms/帧、上限 5–8fps，我们复现出同样的数字。
换成 LZ4 后 decode 降到 23.19ms，整帧 50.88ms，19.7fps。

一笔 5 倍的账，代价是压缩率差一点（同样的画面 zlib 更小）。在这个场景里，
**仪表那颗 2014 年的 CPU 比车机到仪表的百兆链路更稀缺**，所以宁可多传。

### 3.2 DIRECT 直写：19.7 → 23.5fps

原来每帧都走一遍「解压到中间缓冲 → 缩放到面板尺寸 → 拷进 fb」。
发送端按矩形出帧之后，尺寸本来就一致，缩放这一趟纯属浪费。

命中条件 `w==1920 && h==midH && stride==3840 && rawlen==midH*stride` 时，
`lz4DecodeFix` 直接解到 `d.back[bandOff:bandEnd]`。
`DIRECT_VERIFY` 用逐字节比对确认与「解压+缩放」完全一致（`diff_bytes=0`）才敢默认开。

### 3.3 双核流水线：20.3 → 22.9fps（收益远小于预期）

串行时每帧三段：read 1.2ms + LZ4 解码 24.6ms + 整带写 fb 21.9ms ≈ 48ms。
看着是典型的「解码和写屏可以并行」，理论上该到接近 2 倍。

实际只涨了 13%。原因：两个核在抢内存带宽，并行后各自慢 10–15%，
净收益被吃掉大半。**这颗 SoC 的内存带宽比核数更早见顶。**

写 fb 必须单 worker 串行，多线程写会撕裂 —— 这不是性能选择，是正确性要求。

### 3.4 ICBANDS 250 → 1200ms：22.9 → 27fps（单笔收益最大）

每次整幅 `flush()` 要把 fb0 的上下条和中间带一起刷一遍，15–20ms。
原来 250ms 做一次，等于**每 5 帧就白吃一帧**。

改成 1200ms 后涨到 27fps —— 比双核流水线那一大坨改造收益还高。
教训是：**别只盯着每帧的耗时，还要看「多久做一次」**。周期性开销在 60fps 下会被放大 4 倍。

### 3.5 矩形出帧：30.1fps（接收端第一次真正追平发送端）

前几步都是在仪表侧省时间。这一步换了思路：**减少每帧的绝对数据量**。

发送端按仪表实际矩形出帧（`compose ... 750 220 550 384`），仪表侧只贴那一块，
矩形外由 `repaintOutside()` 用 fb0 补回来。750×384 的矩形对 1920×720 的面板，
像素量只有 1/6。

此时 `30.1fps` 恰好等于发送端的 `targetFps=30` —— 天花板已经换人了。

### 3.6 v1.0：30.1 → 58.6fps

两端同时动。这是唯一一次改动量最大、收益也最大的一轮。

**接收端：每帧把 1.47MB 写了两遍。**

```go
copy(d.fb[off:end], d.back[off:end])   // ① 写进 mmap 的 fb
d.writeBack(off, end)                  // ② pwrite 到 /dev/fb1
```

② 才是上屏路径（`writeBack` 的注释早就写了：mmap 区域与硬件实际扫描的显存可能不一致）。
① 是历史遗留 —— 早期以为 mmap 才是路径，后来 pwrite 赢了，copy 忘了删。
1.47MB/帧的重复写，纯烧显存带宽，默认删掉（`ICFBCOPY=1` 可恢复做对照）。

**接收端：整宽行改成按矩形窄写。**

`flushFrame` 原来按整宽行写：1920 宽里只有 550 宽是投屏内容，
每帧 1.47MB 里有 1.05MB 是左右两侧的原仪表画面 —— 那些内容根本不需要重写。

改成 `writeBackRows` 按 `dstW` 窄写：384 行 × 1100 B = **422 KB**。
代价是 384 次 pwrite（每次 3–5 µs，约 1.5ms 系统调用开销），换回约 10ms 的显存带宽。
任一行写失败就整块重写兜底，宁可慢也不留花屏。`ICROWS=0` 退回整宽。

`flush` 从约 22ms 掉到 **3.2ms**。

**发送端：省掉一次整帧中转 + 21 万次循环。**

565 路径原来是 `copyPixelsToBuffer → px（422KB 中转）→ 逐字节循环 21 万次 → frame565`。
`frame565` 本身就能包成 ByteBuffer，直接落进去，只剩一次原地扫描（色键 0→1）。
60fps 下这一趟值 3–4ms。

**发送端：`targetFps` 30 → 60。**

单帧 `procMs` 5–7ms，16.7ms 预算吃得下。撑不住会自动落到实际能到的帧率
（`used < gap` 才 sleep，跟不上就连续采集不再等），不会比 30 更差。

**发送端：LZ4 匹配后不要给整个区间补登记。**

这一条是当轮的真凶，也是唯一一个「算法级」的坑：

```java
int end = ip + len;
for (int p = ip + 1; p < end && p < mfLimit; p++) {
    table[hash(src, p) & (HASH_SIZE - 1)] = p;   // 匹配区间逐位置重新 hash
}
ip = end;
```

画面里大片渐变/纯色的匹配长度动辄几百字节，这个循环等于**整帧每个字节 hash 了两遍**。
改成只补前 4 个位置（标准 lz4 fast 干脆完全不补）后：

| | 改前 | 改后 |
|---|---|---|
| 压缩率 | 120KB/帧 | 117KB/帧 |
| `txLoop` 吞吐 | 47fps | **62fps** |

压缩率只掉 2.5%，发送线程当场追平采集端。顺带把哈希表从「每帧 `new` 128KB + fill」
改成静态复用。

**结果：30.1 → 58.6fps，`total` 14.4–17.2ms。**

### 3.7 剥离自绘 UI 后：59.9fps（确认没有回归）

把接收端里属于另一条技术路线的东西拆掉（卡片绘制、三张 PNG 的 `//go:embed`、
`localmap` / `split` / `jbench` / `fbput` 四个子命令），二进制 3.40MB → 2.36MB。

复测 59.9–60.5fps，**比带卡片的版本还略高**。卡片绘制本来就在 `cards=0` 路径之外，
省下的是代码体积和指令 cache。`flush` 仍 3.0–3.4ms，7860 帧无衰减。

`compose` 的命令行签名保持不变，`cards` 参数接受但忽略 —— 车上 APK 已经写死了这个调用，改参数就得连 APK 一起换。

## 4. 试过但没用的（别再走一遍）

| 猜测 | 验证方式 | 结论 |
|---|---|---|
| 「5–8fps 就是仪表天花板」 | 换 LZ4 后 19.7fps | 那是 zlib 的前提，不是硬件的 |
| 每帧 `FBIOBLANK(0)` 是瓶颈 | `ICSUBMIT=none` 关掉 | 帧率一点没变 |
| `FBIOPAN_DISPLAY` 能省拷贝 | 调用恒 `EINVAL` | `virtual == visible`，没有可 pan 的偏移 |
| 每帧 `FBIOPUT_VSCREENINFO` | 实测 | 无效 |
| 在仪表侧做合成（渐变/卡片/bands） | 实测 | 只有 8.3fps，**不该在仪表合成** |
| 双核流水线能翻倍 | 实测 | 只涨 13%，内存带宽先见顶 |
| 让仪表自己缩放更灵活 | 与发送端按矩形出帧对比 | 发送端用 GPU 缩，质量与时延都更好 |

## 5. 两个差点埋进去的回归

**色键修正不能从发送端挪走。**

为了省那 21 万次循环，我原本想把「0 像素改成 1」整个交给接收端做
（0 是仪表前景层的色键，漏一个就是个黑洞）。但**接收端走满宽 `direct` 直写时是不查像素的** ——
直写路径只做 `copy`，一个 0 都不会被改。修正必须留在发送端的出帧阶段。

**日志里的分项计时不一定可信。**

仪表侧 `sub` 一栏打出过 36 秒，而同一批的 `total` 只有 16.4ms —— `t4-t3` 不可能大于 `t4-tR`。
换了几种算法都一样，最后确认是内核 3.0.35 的时钟源偶发跳变，单次 `time.Now()` 差分不可信。

现在日志只保留 `read/dec/draw/flush | total`，`total` 与 `frames/elapsed` 同量纲、互相自洽。
**判断性能只信 `total`**，残差栏位直接删掉，不留痕迹误导人。

## 6. 物理上限

- 面板 60Hz，`1000/60 = 16.7ms` 是硬预算，`total` 已经压到 15.8ms
- 车机 `captureDisplay` 单帧 `procMs` 5–7ms（capture 2–5ms + 回读 6–7ms）
- 到仪表一帧 422KB，`bytes/s` 约 7.9MB/s

再往上没有意义。想更快的唯一方向是换编码（H.264 硬编解），但那就不是这个项目了。

## 7. 怎么复现这些数字

```bash
# 车机侧：实际出帧率、采集/发送是否同步
adb shell "grep 'fps=' /data/local/tmp/vdsend.log | tail -3"

# 仪表侧：分项耗时
python probe/icrun.py "grep 'frames=' /tmp/icrecv.log | tail -3"
```

日志字段：

```
frames=7860 59.9fps (recv 550x384) read=1.08ms dec=7.10ms draw=4.15ms flush=3.46ms | total=15.8ms
       │        │            │              │         │         │          │            └ 整帧（与 fps 自洽）
       │        │            │              │         │         │          └ 落屏 pwrite
       │        │            │              │         │         └ blit + repaintOutside
       │        │            │              │         └ LZ4 解码
       │        │            │              └ socket 读
       │        │            └ 接收到的帧尺寸
       │        └ frames / 运行秒数
       └ 累计帧数
```

判断顺序：

1. `fps` 和 `total` 对不对得上（`1000/total ≈ fps`）。对不上说明统计有问题，先修日志。
2. 分项里哪一项最大，先动它。
3. 都压下去了但 `fps` 不动 → 天花板不在接收端，去看车机的 `cap` / `sent`。
