## 0. 摘要（先看这七条）

1. **整体接受**。四类拆分（UI/UX/PERF/ADB）与 6 批计划（B0→B5）按原样执行，不改顺序。
2. **ADB-01 定性为 ROM 侧 adbd 授权缺陷，与我方无关**。实测排除 H1（transport 互斥），并从 adbd 日志拿到直接证据：`prompt currently pending, skipping` —— 授权 prompt 是单槽位且被遗留 pending 占死，而该车机没有授权弹窗 UI。**ADB 模块的「共存」改造取消**，B1 只保留稳定性加固与首次授权提示（新增 ADB-11）。
3. **`asx/` 的边界放宽一格**。原结论「本轮不动 asx」改为：**仅允许新增「只采不发」模式**，且必须证明不影响 LZ4/帧率；否则退回静态预演。
4. **产品定位是 C 端车主自用**。因此 UX-09（引导）、UX-12（停止失败保护）、退出链路是必做项，不是可选项；工程术语全部下移。
5. **`act=` 遥控不再是硬约束**。PC 侧脚本允许同步改造，只要新流程符合期望即可，不要求向后兼容。
6. **通知不做**。第三方 APK 的通知进不了车机通知中心（只收小鹏自家通道，见 §2.4），既然用户看不到就取消，不再为 UX-10 加前台服务。
7. **保活改走包名前缀 + 品牌改造**（新增，见 §2.6）。`applicationId` 改成 `com.xiaopeng.*`、应用名改「仪表投屏」、图标重做。**关键实测**：非平台签名 APK 一律被 `pm install` 拒绝，但**走图形安装器可正常安装**，前缀本身不拦。

## 2. 对审计结论的修正（7 条，下一轮必须按这里执行）

### 2.1 ADB-01：定性为 ROM 侧 adbd 授权缺陷（**不建议改 ADB 模块**）

> **结论先行**：`adbprobe` 不需要为「与其他 adb 应用共存」做任何改造。B1 的「共存」子项**取消**，C-2 冲突**消解**。

#### 证据一：排除 transport 互斥（H1）

| 步骤 | 操作 | 结果 |
|---|---|---|
| 对照 | PC 侧 adb 常驻在线 | 命令正常（作为全程常量对照） |
| E2 | adbprobe 点「连接」 | 日志：`token 20B 用 raw 签名（第 1/3 种）` → `已连接 127.0.0.1:5050` |
| E2+ | **在 adbprobe 持有 socket 期间**，PC 侧新建连接并执行命令 | **成功**：`echo PC_ALIVE` 返回，`getprop ro.serialno` = `d66cbf5e` |
| 复查 | PC 连上后再看 adbprobe | 仍显示「已连接」，无断线/重连日志 |
| 结论 | adbd **同时服务 ≥2 个 host** | **H1 不成立** |

#### 证据二：adbd 授权 prompt 单槽位（决定性）

```
11:42:17.778 adbd : prompting user to authorize key
11:42:17.778 adbd : adbd_auth: sending prompt with id 615
11:42:17.778 adbd : adbd_auth: prompt currently pending, skipping   ← 请求被直接丢弃
11:42:25.025 adbd : host-16: read failed: Connection reset by peer
11:42:25.026 adbd : host-16: offline                                ← 8 秒后超时断开
11:42:47.805 adbd : adbd_auth: sending prompt with id 616
11:42:47.805 adbd : adbd_auth: prompt currently pending, skipping   ← 再来一次仍被丢弃
11:42:57.203 adbd : adbd_auth: loading keys from /data/misc/adb/adb_keys
11:42:57.204 adbd : adb client authorized                           ← PC 直接通过（key 已在表中）
```

由此确定：

1. adbd 的授权请求是**单槽位**——已有 pending 时，新请求被 `skipping` 丢弃。
2. 当前槽位被一个**遗留 pending** 长期占死，不释放。
3. 该 pending **没有任何 UI 载体**：`cmd notification list` 里没有 adb 授权通知，`dumpsys activity activities` 里没有授权 Activity，`dumpsys window` 里没有相关窗口 → 用户**无处可点**。
4. 结果：**只有 `adb_keys` 中已有 key 的宿主能连**（我的 PC、adbprobe），其他应用一律 8 秒超时。

#### 证据三：业务侧反证（P7 SHOW，adbprobe 未运行）

- P7 SHOW 设置页（点日期进入）有「ADB 车辆数据」：`127.0.0.1 : 5050`，状态 **「ADB 连接：关」**，下方提示「ADB 配对等待中，请在车机弹窗点击允许」。
- **关键**：此时 adbprobe 进程数为 0（已 `am force-stop`），点连接依然为「关」→ **反证：这不是 adbprobe 的影响**。
- 其请求 id 615 / 616 在 adbd 日志中同样被 `skipping` 丢弃。

#### 假设重排（替代审计 §5）

| 原假设 | 判决 | 依据 |
|---|---|---|
| H1 transport 互斥 | ❌ **排除** | PC 与 adbprobe 可同时在线 |
| H2 授权键被覆盖 | ⭕ **部分成立**，但表现不同 | 不是「旧键被顶掉」，而是「新宿主无法完成授权」 |
| H3 5037 端口冲突 | ❌ **排除** | P7 SHOW 未启动 adbprobe 时同样失败 |
| H4 fd 耗尽 / H5 ROM 风控 | ❌ 基本排除 | 失败点在 AUTH 阶段，不是连接/资源阶段 |
| **真实根因** | ✅ | **ROM 的 adbd 授权 prompt 单槽位 + 遗留 pending 无 UI 可消 + 车机无授权界面** |
| **是否我方责任** | — | **否**。adbprobe 使用 `adb_keys` 中已有 key，不触发新授权请求 |

#### 对 B1 的调整

| 原内容 | 调整后 |
|---|---|
| ADB-01「共存改造」（让出 adbd、按需连接、N 秒断开） | **取消**。不需要为共存改连接策略，长连接可以保留 |
| C-2 冲突（ADB-01 vs PERF-03/04） | **消解**，不再需要「用数据选 N」的取舍实验 |
| ADB-02 / 03 / 06 / 07 / 10 | **保留**。这些是掉线、残留、解析健壮性问题，与共存无关 |
| **新增 ADB-11** | **首次授权失败必须显式提示**：AUTH 超时或拿不到 prompt 响应时，UI 明说「车机侧未弹出授权窗，请重启车机或改用已授权 key」，**禁止静默重试**；同时不再盲目尝试 3 种签名模式（现日志显示第 1 种 raw 已成功，后两种是浪费） |
| **新增 ADB-12（重要）** | **禁止对「已在 adb_keys 中的 key」再发 `AUTH_RSAPUBLICKEY`**。该动作会在 adbd 里生成一次「等待用户确认」的 prompt；本 ROM 的 prompt 没有可见 UI 可消，**一旦槽位被这种 pending 占住，后续所有新授权都会被 `skipping` 直到复位**（13:20 修正：可恢复，非永久损坏，见下「复位结果」）。判定方法：连接前先用已有 key 走 `AUTH(TOKEN)`→`AUTH(SIGNATURE)`，只有签名失败才允许走公钥路径，且**只允许一次** |

#### 证据四：受控复现（2026-11-05 12:04，用全新密钥）

为确认「遗留 pending」不是已经自愈，把 PC 侧密钥临时换成一把全新 RSA 密钥再连：

| 步骤 | 结果 |
|---|---|
| 新密钥连接 | `failed to authenticate`，设备侧 `unauthorized` |
| adbd 日志 | `prompting user to authorize key` → `sending prompt with id 647` → **`prompt currently pending, skipping`** |
| 再试一次 | id 648，同样 `skipping` |
| system_server 侧 | `logcat -b system` 里**没有任何 `AdbDebuggingManager` / `UsbDebugging` 记录** → 授权请求根本没进到弹窗流程 |
| 结论 | **（复位前）**槽位被占死，且不是偶发；任何未预授权的新 key 都失败。**该结论已于 12:49 复位后推翻**：同一通道能正常发 prompt、能拿到 OK、能释放（见下「复位结果」），说明这是遗留 pending 造成的可恢复状态，不是 ROM 永久缺陷 |

> 测试后已还原原密钥并重新连接，设备状态无残留。

#### 复位手段（实测，替代原「需 root」的说法）

`/system/etc/init/init.system_xpeng.rc` 里有一条现成的复位通道：

```
on property:sys.xp.adb.tcp.port=5050
    setprop service.adb.tcp.port 5050
    stop adbd
    start adbd
```

- ✅ **有效**：触发后 init 会 `stop/start adbd`，adbd 状态机重置，端口保持 5050。
- ❌ **adb shell 写不了**：`setprop sys.xp.adb.tcp.port 5050` 返回 `Failed to set property`（SELinux 拒绝，shell 域无权限）。
- ❌ **shell 也杀不掉 adbd**：`kill -0 7885` 直接 `Permission denied`（虽然 adbd 与 shell 同为 uid 2000，但 `u:r:adbd:s0` 不允许 shell 发信号）。
- ❌ **`setprop service.adb.root 1` 无效**：本 ROM 没有该属性的 init 触发器，adbd pid 不变。
- ❌ **`setprop ctl.restart adbd`**：`Failed to set property`。
- ✅ **唯一可用途径**：由 **system uid 的系统应用**去写该属性——即「开发者工具（`com.xiaopeng.devtools`，uid 1000）」里的**无线 ADB 开关关掉再打开**，或**直接重启车机**。

#### 运维侧处置（写进 README，不改代码）

某应用突然需要重新授权且一直超时时，按序处置：

1. 断开所有 host（含 PC 侧 `adb kill-server`）；
2. **重启车机**，或在开发者工具里把「无线 ADB」关掉再打开（走的就是上面那条 init 触发）；
3. ⚠️ **重启后需确认 5050 是否还在**：`service.adb.tcp.port` 是由 `sys.xp.adb.tcp.port` 触发设置的**运行时属性**（非 `persist.`），若车机起机后没人重新写它，无线 adb 不会自动回来。届时需在开发者选项里重新打开一次；
4. 重新连接后**不必刻意回避新授权**（13:20 修正）——新 key 授权本身是正常路径，本机 12:58 已跑通；只是别在没有必要时反复用新公钥去试探，那样会多留一张需要复位的 pending。

> **限制说明**：该车机为 user 版、无 root，无法读取 `/data/misc/adb/adb_keys`（`Permission denied`），因此「键表里到底有几把、有没有损坏条目」无法直接验证。日志中出现过一条 `Invalid base64 key`，说明该文件至少有一个格式非法的条目，属 ROM 侧问题。

#### 复位结果（2026-11-05 12:49，已复现成功，本条结论闭环）

操作人：用户；方式：**开发者工具里把「无线 ADB」关掉再打开**（未重启车机）。

| 观察点 | 复位前 | 复位后 |
|---|---|---|
| adbd pid | 7885 | **13822**（中间还有一次 13777，对应「关」→「开」两跳） |
| 车机 uptime | 1 天 15 小时 | **仍 1 天 15 小时**（确认未重启，只是 adbd 重建） |
| `service.adb.tcp.port` | 5050 | **5050**（端口未丢） |
| `sys.xp.adb.tcp.port` | 空 | 空（init 触发器消费掉后不留残值） |
| `service.adb.root` | 0 | 0 |
| 授权框架连接 | — | 12:49:18 `adbd_auth: received a new framework connection`（system_server 重新接上） |
| 授权槽位 | 一直 `skipping` | **正常**，见下 |

**授权槽位实测（12:58:11，真实的一次 prompt 往返）**

```
12:58:11.669  host-36: already offline
12:58:11.669  Calling send_auth_request...
12:58:11.674  adbd_auth: loading keys from /data/misc/adb/adb_keys
12:58:11.674  E adbd: Invalid base64 key
12:58:11.674  Calling send_auth_request...            ← 第一次验签失败后重试
12:58:11.675  prompting user to authorize key
12:58:11.675  adbd_auth: sending prompt with id 17
12:58:11.675  adbd_auth: marking framework writable
12:58:14.640  adbd_auth: received packet: OK
12:58:14.640  adb client 17 authorized                ← 3 秒内通过
12:58:14.641  adbd_auth: no prompts to send           ← 槽位正常释放
```

**三条结论**

1. **死锁是遗留状态，不是 ROM 的永久缺陷**。复位后同一个 prompt 通道能正常发出、正常拿到 OK、正常释放——审计原假设里「ROM 授权机制天然不可用」这一支**被证伪**。
2. **`Invalid base64 key` 是持续存在的坏数据**。它出现在 `loading keys` 之后、且每次都会导致一次「先失败再重试第二遍 `send_auth_request`」。复位后计数归零的只是缓冲区，不是缺陷本身。这意味着：**只要那条坏记录还在 `adb_keys` 里，每次新宿主连接都会多走一轮验签失败**，虽不致命，但会让首次连接变慢、并放大偶发超时的概率。无 root 无法清理，只能记录。
3. **复位不丢 5050**（这次实测明确），所以「关开无线 ADB」比「重启车机」更优：不断电、不动其它应用、端口保留。

**复位后的功能验证（同一时段）**

|---|---|
| PC 侧 `adb connect` + 执行命令 | ✅ 正常 |
| 应用内「连接」按钮 | ✅ 日志打出 `已连上 127.0.0.1:5050`，`/proc/net/tcp6` 出现 `127.0.0.1:5050 ← 127.0.0.1` 的 ESTABLISHED |
| 本次连接是否需要新授权 | ❌ 不需要（应用 key 已在 `adb_keys`，无 prompt、无 `skipping`） |
| 「状态」按钮 | ✅ 返回车机网口信息（`inet 172.20.1.45/24 ... eth0`） |

### 2.2 `asx/` 边界：从「不动」改为「受控改动」

- **允许**：给 VdSend 新增「只采不发」/`--no-send` 模式，用于启动前实时预演。
- **硬约束**：不得改动 LZ4 编码、icrecv 的 dec/draw/flush、单槽队列背压、`compose` 参数顺序、5560 协议。
- **准入条件**：必须先用 PERF 数据证明「开启预演时投屏帧率不回退」（车机 ≥60fps、仪表 ≥58fps）。**达不到就退回静态预演**（`fb0_pre.png` + crect 摆位合成）。
- **决策路径**（对应 C-4 冲突）：B4 先做静态预演（0 风险、必交付）→ 同时在 B5 评估只采不发 → 数据达标才替换为实时预演。两者 UI 一致，切换只换数据源。

### 2.3 UX-11 遥控入口：从「硬约束」降级为「同步改造」

- PC 侧 `tools/*.sh` 允许随新流程一起改，不要求保留旧 `act` 语义。
- 但要求：**同一套动作在 APK 与 PC 脚本上都存在且命名一致**（改完两边都能跑通同一条用例），避免历史上「脚本 7 步 / APK 8 步」的漂移（审计 §1.3 已指出该问题）。
- 若删除某个 `act`，必须在批次收尾的 CHANGELOG 写明。

### 2.4 UX-10 通知：**取消**；保活改走包名前缀

**决定（2026-11-05 12:30，R5-1）**：**不做前台服务、不加常驻通知。** 理由两条：

1. 用户根本看不到——车机通知中心只收小鹏自家通道，第三方 APK 的通知进不去；
2. 保活改由 `com.xiaopeng.*` 包名前缀承担（§2.6），不必再靠前台服务提优先级。

#### 实测证据（保留备查）

| 项 | 结果 |
|---|---|
| 系统版本 | **Android 12（SDK 32）**，APK `targetSdk=28` |
| 运行时权限 | **不需要**。`POST_NOTIFICATIONS` 是 API 33 引入，本机 SDK 32 且 targetSdk 28 |
| 通知栏下拉 | 调出的是「车辆控制中心」（后备箱 / 大灯 / 快充 / 哨兵模式 / 360影像 / 等人模式…），**没有任何通知卡片**；`cmd statusbar expand-notifications` 同样无效 |
| 通知中心是否存在 | **存在**。状态栏蓝牙左侧有**铃铛图标**（有未读时带红点），点击弹「通知中心」浮层 |
| 谁能出现在通知中心 | **只有小鹏自家通道**。实测唯一可见的是 `com.xiaopeng.aicabinservice / channel=AIAssistant Notify`；`cmd notification post` 投的同内容通知（`com.android.shell`）**不出现**，`com.xiaopeng.ota` 的系统更新通知也不出现 |
| 判定依据 | 通知记录里的厂商字段 `displayFlag`：能显示的是 `0x20`，其余（含所有前台服务通知）是 `0xffffffff` → 被过滤 |
| 结论 | 车机有通知中心，但**第三方 APK 的通知进不去**（`com.xiaopeng.providers.notification` 的 `WRITE_NOTIFICATION` 是系统权限） |

#### 一条技术澄清（避免下一轮误判）

「通知做不到」严格说只对**展示**成立：即使通知不可见，`startForeground()` 依然合法，也依然能提升进程优先级。

所以如果 §2.6 的前缀保活实测不成立，**回退方案就是加前台服务**：manifest 一条 `FOREGROUND_SERVICE` + 一个通道 + 一条通知，约 20 行，无运行时权限弹窗。**该回退只在 B0.5 验证失败时启用**，不要提前做。

#### 不改的底线

「投屏中」状态必须在**主界面**可见；不得依赖通知、状态栏或任何系统级提示（车机上这些地方都不归我们管）。

- 日志区默认折叠为一行摘要，出错自动展开；保留诊断模式（连点 5 次）。

#### 关于「前缀即保活」的可信度

这是平台侧经验结论（R5-1），我核了一遍系统配置：`/system/etc/sysconfig/allow-persistent-packages.xml` 是一份**显式包名列表**（43 条，全是系统应用，既不含 `com.xiaopeng.adb` 这种后装包，也没有任何前缀规则）。也就是说保活**不走这份配置**，更可能是 framework 层按前缀放行。

因此本项按「**已知有效、仍需实测**」处理：B0.5 的 DoD 就是拿 30 分钟后台存活对照把它证成或证伪（见 §6 第 9 项）。

#### 为什么必须最早做

后续所有测量、PC 脚本、截图、DoD 都以**新包名**为准。B0 基线如果按旧包名采，改完包名全部作废重跑。因此作为 **B0.5** 插在 B0 与 B1 之间。

#### 实测结论（关键，别踩）

ROM 对**非平台签名**的 APK 一律拒绝 `pm install`，与包名前缀无关：

```
# 目标包名
isByAdb:true DISPLAY:XMARTQXZHE28F5_V5.10.5.8804_..._USER_Release isPlatSigned:false cannot install: com.xiaopeng.vdcast

# 对照包名（同样被拒，证明不是前缀的锅）
isByAdb:true DISPLAY:... isPlatSigned:false cannot install: com.probe.pkgtest
```

而走**图形安装器**（`tools/installapk.sh`，即 `com.android.packageinstaller/.PackageInstallerActivity` + 键盘导航）后：

```
=== 第 1 轮：调起安装器 ===
  安装器已在前台
=== OK 已更新 ===
    lastUpdateTime=2026-11-05 12:29:34
```

→ **`com.xiaopeng.vdcast` 已成功安装**（测试后已 `pm uninstall` 清理干净）。这也解释了 `com.xiaopeng.adb`（小鹏adb，非系统包、uid 10100、`installerPackageName=com.android.packageinstaller`）为什么能带小鹏前缀。

**由此得到三条硬约束：**

1. **前缀不拦人，签名拦人**。`com.xiaopeng.*` 本身可以装，不会因为前缀被拒。
2. **安装通道唯一＝图形安装器**。`adb install` / `pm install` 永远失败，不要提供这类快捷方式；
3. 顺带一个小坑：APK 若声明了 activity 却没有 `classes.dex`，装到最后会以 `PackageManagerException: ... code is missing` 失败。改包名时若临时做了个空壳包验证，记得加 `android:hasCode="false"`。
