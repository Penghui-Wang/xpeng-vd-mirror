## 2. 三个结论（都比原计划更重要）

### 2.1 「2 次 RPC ≈3.5s」已经过期，别再按它优化

- `[4/8]` 的 1.83 s 只在**要真去仪表核对二进制**时出现（17:19 那次就是）；稳态下走的是
  「与上次投送的版本一致（本地记录命中），跳过核对」，实测 **0.26 s 且一次 RPC 都没发**。
- 现在每次启动实际只有 **2 次 Icrpc**：`[5/8]` 起接收端（0.48 s）、`[7/8]` 等出帧（2.0 s，其中大部分是等日志出现）。
- 所以「砍 RPC」即使砍到 0，也只能省 **~2.5 s**，而且要把「确认真的出帧」这条安全判据一起砍掉 —— 不建议。

### 2.2 真正的两个大头：VdSend 起屏 1.9 s + 接收端首帧计数 2.0 s

- `[6/8]` 的 1.9 s 是 VdSend 真跑出来的（dex 加载 + 建虚拟屏 + 搬窗口 + capture 就绪），
  轮询已经是 0.2 s 粒度，没有「白等」。
- `[7/8]` 的 2.0 s 几乎全是**等接收端打第一行 `frames=`**：icrecv 每 60 帧打一行，
  35 fps × 60 ≈ 1.7 s，加 0.2 s 轮询 ≈ 2.0 s —— 数字对得上。
  → 让接收端在**第 1 帧**就打一行（之后仍每 60 帧），这段能掉到 0.3 s 左右，
  这是目前看到收益最大、语义最安全的一刀（判据仍是「真的收到帧」）。

### 2.3 帧率：**门槛已取消**（18:01 车主改口径）

四轮实测（仪表端）：34.2 / 34.9 / 31.1 / 34.7 fps（中位 34.5），车机侧 59–60 fps，
单帧 `read 5.2 + dec 12.4 + draw 6.6 + flush 4.4 = 28.6ms`。

车主 18:01 明确：**对帧率没有要求，不存在「默认安全区 ≥58fps」这条**；
唯一的要求是「**安全区不能全覆盖仪表**」。所以 16:20 定的 58fps 验收线作废，实测值只作记录。

## 3. 附带发现：停止路径会偶发卡满 45 s

4 轮里有 **2 轮** stop 在 `[1/4] 停车机发送端` 卡到 adb 的 45 s 读超时，然后报：

```
17:53:45.615  !! 停止中断: SocketTimeoutException: Read timed out
17:54:55.567  !! 停止中断: SocketTimeoutException: Read timed out
```

两次超时后立刻重发 `stop`，**0.9–1.0 s 就完成并 `RESTORE_OK`**；车机上没有残留 VdSend、也没有残留虚拟屏。
卡住的位置是 `killvds.sh stop` 里前台跑的 `app_process --restore`（等它退出）。

- 影响：用户点「停止」会看到「收尾未完成」，得再点一次；这不是新回归，B1 取消时就记过「长任务不可中断」。
- 建议：B5 里给 `[1/4]` 单独设**更短的超时**（如 15 s）+ 超时后直接 `kill -9` 残留再走「确认恢复」，
  把「卡 45 s」压成「15 s 内一定有结论」。这条属可靠性，不是提速，但收益比省 0.3 s 大。

## 7. 根因：同一条 Adb 连接上并发跑两条 stream，会互相吞掉对方的 CLSE

### 7.1 结论（一句话）

**不是 `killvds stop` 慢，也不是 restore 卡住；是 APK 的 Adb 客户端在「一条连接上并发跑两条命令」时，
把另一条命令的收尾包当成「别的流」丢掉，那条命令就永远等不到结束，一直到读超时。**

### 7.2 怎么锁定的

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① 直连复现 | PC 侧 `adb shell sh killvds.sh stop` 跑 8 轮 | 8/8 正常（4.6–4.9s），说明**不是命令本身慢** |
| ② 走 APK + 每秒采样 | `act=stop` 跑 10 轮，每秒抓进程树 | 0/10 复现（采样本身拖慢了 restore，没撞上窗口） |
| ③ 加压只检测 | `act=stop` 跑 30 轮 | **0/30**，全 5.9–7.2s |
| ④ 故障注入 | 把 3 秒补测临时改回**旧版裸线程 `a.exec`**（与 stop 并发） | **第 1 轮就复现**：`停发送端超过 15000ms`，收尾 15976ms |
| ⑤ 加锁对照 | 保持④的代码，给 Adb 的流操作加 `synchronized` | **8/8 正常**（5.9–6.5s），不再超时 |
| ⑥ 最终包 | 锁 + 补测改回 worker（从源头不并发） | 4/4 正常，启动 3.0s，小灯 3.3s 内补齐 |

### 7.3 机制

`Adb.readAll()` 只处理 `arg1 == 自己流` 的包，其余一律 `continue` 丢掉：

```java
if (p.command == CMD_WRTE && p.arg1 == s.local) { ...收数据... }
if (p.command == CMD_CLSE && p.arg1 == s.local) { ...结束... }
// 其它流的包：直接忽略
```

两条命令并发时，A 线程会把 B 流的 `WRTE`/`CLSE` 读走并丢弃；B 永远等不到 `CLSE`，
直到 `SocketTimeoutException`。而 `execRc` 的超时会把整条连接 `close()`，
后面的「kill -9 / 二次 stop / 残留检查」全部报「未连接」—— 这就是 17:53 那两次「收尾直接中断、接收端留在仪表上」的来历。

### 7.4 时间线对得上

两次历史卡死都发生在「start 完成后约 2.5s 发出 stop」：补测在 start 后 **3s** 触发，
正好落在 `[1/4] killvds stop` 那 4.3s 的窗口里。补测一挪进 worker 就再也撞不上 —— 这也解释了为什么
B5 改完之后 30 轮都复现不出来。

### 7.5 修法与验证

1. `Adb.exec / execRc / push / pull / connect / close` 全部 `synchronized` —— 就算以后又有人在别的线程直接调，
   也只会排队，不会互相吞包（这是**根因修复**）。
2. 3 秒补测改走 `worker` —— 不再与 stop 并发（这是**去掉触发条件**）。

验证就是上表 ④⑤⑥ 三组对照，代码与日志在 `docs/materials/b5/repro/`。

## 8. 第三批：停投屏 4.95s → 1.69s（同样的思路：把固定等待换成数据驱动）

| 位置 | 原来 | 现在 |
|---|---|---|
| `killvds.sh`：TERM 后等进程退出 | `sleep 2` | 轮询到「真的没有 VdSend」（上限仍是 2s） |

### 8.2 踩到的坑（自己挖的）

第一版把 `sleep 2` 换成 `list | wc -l` 轮询，结果**永远看到 1 个进程**、20 轮跑满 2 秒 —— 因为那条
