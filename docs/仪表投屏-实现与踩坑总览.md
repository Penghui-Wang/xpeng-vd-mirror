# 小鹏 8295 车机 → 仪表投屏：实现与踩坑总览

> 时间跨度：2026-10-30 ~ 2026-11-02
> 目标车型：小鹏 E28U（高通 8295 / Android 12）
> 仪表：i.MX6 Dual（ARMv7 / Linux 3.0.35）
> 文档定位：把三天里所有跑通的路线、被推翻的判断、踩过的坑、实测数据集中到一处，避免下次重复试错。

---

## 0. 一页速览

| 项 | 结论 |
|---|---|
| 最终可用方案 | 车机主屏 `SurfaceControl.captureDisplay` 主动截屏 → RGB565 → LZ4 → TCP → 仪表 fb1 中间带 |
| 车机采集 | **稳定 30fps**，单帧处理 11–12ms，2000+ 帧零失败 |
| 仪表显示 | QQ音乐界面 **24–27fps**；全屏地图 **17fps**（压缩率差、payload 大） |
| 链路码率 | 4.0 ~ 7.8 MB/s（32–62 Mbps），百兆网够用但不宽裕 |
| 显示区域 | 仪表中间带 y=72..640（1920×568）；上下条从 fb0 原样拷贝（顶条含档位与全部原厂警示灯，不重绘） |
| 一键启动 | `bash tools/startcast.sh` |
| 最大隐藏坑 | **进程必须由 shell 域启动**（`adb shell` + setsid）；售后域 root 启动会在几百帧后失效 |
| 已放弃路线 | 虚拟屏 + ImageReader（2fps 天花板）、CarLife smali 补丁（依赖 CarLife）、镜像 VD（不出帧） |

### 1.3 风险边界（这套东西到底动了仪表什么）

30510 是无鉴权的 root shell 通道，写入会直接影响仪表（安全件）。所有实验必须**驻车**进行。
下面是这句话的准确展开——风险落在哪、没落在哪，别混着说。

**A. 没有碰的东西（不会变砖）**

| 项 | 状态 |
|---|---|
| 固件 / 分区 | 完全没写。没刷 boot、没动 `/system`、`/vendor`、没改 SELinux 策略 |
| 仪表主程序 `ECluster` | 没替换、没 hook、没改资源 |
| 车辆总线 | **只读不写**。用 `Properties.Get` 读车速、档位、SOC、行程、告警 ID（`com.xiaopeng.DomainController.Cluster`）；不发任何写请求，不碰 CAN |
| 仪表侧落盘 | 只有 `/tmp/icrecv_dbg`（**tmpfs，重启即消失**）+ `/tmp/icrecv.log` |
| 车机侧落盘 | 只有 `/data/local/tmp/vd.dex`（一个 dex，不装、不注册、不开机自启） |

结论：**断电重启就回到原厂状态**，不需要卸载、不需要刷机。

**B. 确实在发生的事**

1. **画面遮盖**——中间带 `y=72..640`（568 行）整块由我们画。原厂这块在**开导航时放的是地图 + 转向指引**（见 `shots/ic_now.png`：左转 56m「无名道路」+ 高德鹰眼守护）。
   投屏期间这些看不见了。上下两条（`0..72` / `640..720`：READY、PRND、手刹灯、温度、驾驶模式、电量、续航、时间）是**从 fb0 原样拷贝**的，不受影响。
2. **占仪表 CPU**——实测 loadavg：只有投屏链路时 ≈4.7；再叠数字层（每秒约 7 次 dbus fork）与顶条搬运后 8.5–8.7。
   单看绝对值会误判：这台仪表**开机基线就有 ≈7.6**（原厂 ECluster + 地图），所以有意义的是增量 **≈1.0**，落在 200ms 周期里每拍 101ms。
3. **原厂弹窗被替换成我们画的**——图形类警示灯（车门、安全带、胎压、ESP、车道、EPB）由顶条整条抄 fb0 覆盖，自动齐全；**文字告警**（「ESP功能受限，请联系售后」这类）由告警层按两路 ID 复现（197 条文案）。
   抄不到的是**带动画/自定义布局的弹窗**（车辆俯视图、四轮胎压图）—— 遇到只能回退到「让原厂画一会儿」。

**C. 没有验证过的（别当成结论）**

- **真实文字告警没在实车上触发过**。两路 ID 一直是 255，验证只做到 `DASH_ALERT_TEST` 强制上屏、确认落点与可读性。
- `host_bcm_door` 是四元素数组，下标与四扇门的对应关系**没测**（别按常规顺序想当然）。
- 30fps 重绘的双核余量、撕裂程度，没有做过长时压测。

上车正式用之前，这三条要么驻车观察确认，要么明确「坏了会怎样」再用，不能靠推断。

**D. 为什么必须驻车**

1. 30510 是 root 且**无鉴权**——命令写错就是真改仪表，没有第二次机会，行车中出问题没法停车处理；
2. 遮住转向指引在高速上是实打实的危险；
3. 出异常要恢复原状（`--restore` 搬窗口、重启仪表进程），只能停车做。

## 2. 最终架构

### 2.1 数据流

```
┌──────────────────── 车机 (8295, Android 12) ────────────────────┐
│  QQ音乐 freeform 窗口 [960,0]-[2400,1080]                       │
│              │                                                  │
│              ▼  每帧主动请求                                      │
│  SurfaceControl.captureDisplay(displayToken, args)              │
│    setSourceCrop(960,345,1440,426)                              │
│    setSize(1920,568)        ← 裁剪+缩放由 SF 在 GPU 侧完成         │
│              │  14–16ms（capture 2–5ms + 回读 6–7ms + 转码）      │
│              ▼                                                  │
│  ARGB_8888 / RGB565  →  RGB565 (0 抬成 1，避开前景色键)          │
│              │                                                  │
│              ▼  单槽覆盖队列（丢中间帧，只发最新）                  │
│  LZ4 block 压缩 → ICF1 头(24B) + payload → TCP 172.20.1.40:5560  │
└─────────────────────────────────────────────────────────────────┘
                              │  4–8 MB/s
┌──────────────────── 仪表 (i.MX6, ARMv7) ────────────────────────┐
│  :5560 accept → read 24B 头 → read compressed payload           │
│              │                                                  │
│              ├── goroutine A：LZ4 解码（直写 back 缓冲的中间带）    │
│              └── goroutine B（单 worker）：pwrite 到 fb1          │
│                              │        ← 必须串行，否则撕裂          │
│  每 200ms 一拍（split 模式）：                                    │
│    · 顶条 y 0..72 ← fb0 整条 memcpy（档位/警示灯，原厂自己画）      │
│    · 数字层 读 D-Bus 贴字（右卡 / 底条）→ 只有变脏才刷对应行         │
│    · 中间带：远程帧（QQ音乐/地图）按内容比对，变了才转 565 上屏      │
│  底条 640..720 ← fb0，按需（≈1200ms 兜底）                         │
│              │                                                  │
│              ▼                                                  │
│   fb1 1920×720 RGB565，blend: alpha=255 + colorKey=0            │
└─────────────────────────────────────────────────────────────────┘
```

> 上面是 split（生产）路径的节奏。更早的纯投屏版本 `icrecv_dbg` 没有数字层，
> 上下条统一 `ICBANDS=1200ms` 整幅 flush —— 那个数别再套到 split 上。

### 2.2 关键参数

| 参数 | 值 | 说明 |
|---|---|---|
| `SRC_X/Y/W/H` | `960,345,1440,426` | 车机屏幕坐标，QQ音乐歌词页横条 |
| `OUT_W/H` | `1920,568` | 与中间带一致（1440×426 → 1920×568 同为 3.38，不变形） |
| 中间带 | `y=72..640` | `720 - 72(top) - 80(bot) = 568` |
| fb1 目标 | 1920×720 / RGB565 / stride 3840 / smem 2764800 | 宽屏模式后的几何 |
| ICF1 | `"ICF1"\|w\|h\|fmt\|complen\|rawlen`（u32 LE）+ payload | fmt: 0=zlib 1=raw 2=LZ4 |
| 色键 | 像素值 0 → 1 | 仪表前景层 key=0，纯黑会被抠成透明 |
| 采集目标帧率 | 30 | 目标由循环控制，不受系统重绘节奏影响 |
| `ICBANDS` | 1200ms | **纯投屏版**（`icrecv_dbg`）的上下条刷新间隔，250ms 时每 5 帧白吃一帧 |
| split 节拍 | 200ms | 生产路径：一拍里做完顶条搬运 + 数字层 + 中间带比对，实测 101ms/拍 |
| 顶条搬运量 | 1920×72×4 = 552KB | 每拍 memcpy + 逐字节比对，没变就一个字节都不写屏；抓图 27→28ms |

### 2.3 为什么是「主屏主动截屏」

- **不是虚拟屏**：`VirtualDisplay` + `ImageReader` 已完全从 `VdSend.java` 移除（只剩注释记录失败经过）。
- **不是镜像**：`AUTO_MIRROR` 是被动消费者，等 SF 合成事件；主屏走 HWC 直通时不合成，就 0 帧。
- `captureDisplay` 是主动的：每帧自己发一次请求，SF 立刻合成并回读，帧率由我们控制。
- 副作用：抓的是主屏合成结果，**车机屏幕必须看得见那块内容**；把 QQ音乐 最小化或被别的 app 盖住，仪表会跟着变。

## 3. 采集方案的完整演进（5 条路线）

| # | 日期 | 做法 | 实测 | 结局 |
|---|---|---|---|---|
| V1 | 10-30 | 车机 `screencap` 整屏 → 缩放 → zlib → 仪表 | 10–12fps 预算，实测 ~15fps | 可用但慢，被后续取代 |
| V2 | 10-31 | CarLife 视频帧：smali 补丁挂 ImageReader Surface | 仪表 18.2fps | **可用**，但强依赖 CarLife |
| V3 | 11-01 | `VirtualDisplay`(OWN_CONTENT_ONLY, 2400×1200) + ImageReader + move-stack | 拖动时 9–14fps，静止 **0fps** | 放弃：damage 驱动，天花板 2fps |
| V4 | 11-02 凌晨 | 虚拟屏镜像 `AUTO_MIRROR` | 正常播放 0 帧 | 放弃 |
| V5 | 11-02 | **`SurfaceControl.captureDisplay` 主动截屏** | **30fps 采集 / 27fps 显示** | **当前方案** |
| V6 | 11-02 | 虚拟屏 + 自建 shadow display token（共享 layerStack） | **29fps，1556 帧零失败** | **已验证**，内容独立于主屏，尚未做成正式模式 |

### 3.1 V2：CarLife 补丁路线（仍可用）

- `UltraCap`：smali 补丁挂在 `u8.h.c(String,Surface)` 开头，把离屏 ImageReader 的 Surface 以 id `ultra` 注册进 CarLife 的输出表（`j$/util/concurrent/ConcurrentHashMap`）。解码一次画到所有 Surface。
- `UltraStream`：三段流水（抓帧 / 编码 / 发送），段间「容量 1 投递箱 + 满了丢帧」。
- 抓帧必须 `HardwareBuffer → Bitmap.wrapHardwareBuffer → copy(ARGB_8888) → getPixels`；直接读 `Image.Plane` 是厂商 tiled 布局，出来是规律条纹噪点。
- 坑：同一 Surface 挂第二个 EGL 生产端会把 BufferQueue 抢死；会话重建会 `clear()` 整张表；压缩缓冲要 3 张池化，否则仪表侧报 `lz4 output overflow`。
- 裁切 `x=158 y=500 w=2162 h=663 fps=22`；为了保住车标丢了顶部转向卡（相距 770px，装不下）。

### 3.2 V3/V4：虚拟屏路线为什么停在 2fps

- 内容确实能进虚拟屏：`am display move-stack <RootTaskId> <displayId>` 有效，三条铁证（主屏上 app 消失、主屏切走后虚拟屏仍是它、`input -d` 注入后帧率从 0 涨到 20）。
- 但**合成是 damage 驱动的**：画面静止时 SF 根本不为该屏合成，`ImageReader` 永远等不到 buffer。
- `ImageReader` 回调还是**边沿触发**的：只要一次 `acquireLatestImage()` 返回 null，队列保持非空，之后永不回调 → 采集永久卡死，只能靠看门狗重建。
- 虚拟屏合成帧率与面积强相关：2400×1200 → **2fps**，1440×720 → 7–8fps。
- 结论：软件虚拟屏 + 直接写 fb1 的天花板约 2fps，达不到实时。**必须换成主屏主动截屏**。

## 4. 车机侧实现（`asx/src/com/probe/asx/VdSend.java`）

### 4.1 采集：反射 `captureDisplay`

```java
Class<?> sc    = Class.forName("android.view.SurfaceControl");
Object token   = sc.getMethod("getInternalDisplayToken").invoke(null);
Class<?> bld   = Class.forName("android.view.SurfaceControl$DisplayCaptureArgs$Builder");
Object builder = bld.getConstructor(IBinder.class).newInstance(token);
bld.getMethod("setSourceCrop", Rect.class).invoke(builder, new Rect(960,345,1440,426));
bld.getMethod("setSize", int.class, int.class).invoke(builder, 1920, 568);
Object args    = bld.getMethod("build").invoke(builder);
Bitmap bmp     = (Bitmap) sc.getMethod("captureDisplay", argsCls)
                     .invoke(null, args).asBitmap();
```

- 裁剪与缩放都在 SF 侧完成，CPU 只付回读成本。**不要自己做双线性缩放**，那是白烧内存带宽。
- `setPixelFormat` 不一定存在：探测失败就走 ARGB_8888，再逐像素转 565（多 8–12ms/帧）。
- `capArgs` **只在裁切区变化时重建**。旧版每帧重建并打一行日志，`vdsend.log` 里堆了 19000 条 `args crop`，procMs 从 11 涨到 15。

### 4.2 色键修正

仪表前景层用 colorKey=0 抠透明，所以**任何纯黑像素都会变成透明洞**。转 565 时统一 `if (v == 0) v = 1;`。

### 4.3 发送：单槽覆盖队列 + 独立 tx 线程

原来的致命设计：在 TX 锁内同步做 LZ4 + `out.write()`。仪表一帧要 285ms，TCP 缓冲一满就阻塞，`image.close()` 等不到，ImageReader 的 4 个 buffer 全占满，SF 直接停止提交新帧 → **播放中画面彻底冻住**。

现在：

- 采集只把成品帧 `System.arraycopy` 进单槽队列（`txBuf565` + `txSeq`），立即返回；
- `txLoop` 线程负责压缩 + 发送；
- 单槽覆盖 = 发送慢时自动丢中间帧，永远发最新，**延迟不累积**；
- 无新帧时 250ms 保活重发最后一帧（防止仪表 `i/o timeout` 掉线）。

### 4.4 裁切热重载

`/data/local/tmp/vdcrop.txt` 内容为 `x,y,w,h`。每 15 帧（约 0.5s）读一次比对字符串。

**不能用 mtime 判断**：`adb push` 后时间戳精度可能不变，改了内容也检测不到。

### 4.5 降级路径

`captureDisplay` 连续失败 5 次 → 切 `screencap -d 0`（读 16 字节头 + 2400×1200 RGBA，约 85ms/帧，10–11fps）。screencap 路径的工程细节：

- 子进程 `stdin/stdout/stderr` 三个管道**必须逐个 close**；
- `destroy()` 之后必须 `waitFor()`；
- 否则 fd 泄漏 + 僵尸累积，最后 `ProcessBuilder` 抛 `error=13`（伪装成权限错误）。

### 4.6 启动方式（最关键的一条）

```bash
adb shell "CLASSPATH=/data/local/tmp/vd.dex setsid app_process /system/bin \
  com.probe.asx.VdSend --child 1920 568 30 > /data/local/tmp/vdsend.log 2>&1 &"
```

**必须用 shell 域**。同一份 dex：

| 启动域 | captureDisplay | screencap |
|---|---|---|
| `u:r:xpaftersalesd:s0`（asroot 售后通道） | 约 **330 次后恒返回 null** | 几十帧后 `error=13` |
| `u:r:shell:s0`（adb shell + setsid） | **1500 次零失败** | 3400+ 帧零失败 |

排查过程中排除了内存泄漏（RSS 稳定 124MB）、token 失效（重建无效）、`System.gc()`（无效），最终用「同 dex 换启动域」定性。

## 5. 仪表侧实现（`tools/icrecv2/main.go`）

### 5.1 fb1 切宽屏：只能走 sysfs

`FBIOPUT_VSCREENINFO` 被 OEM 禁用，必须：

1. 向 `/sys/class/graphics/fb1/modes` 写 **112 字节**（2 个 `videoMode` 结构，各 56B）`[fb1 当前模式, fb0 背景模式]`；
2. 向 `mode` 写 `"U:1920x720p-60\n"`；
3. 恢复：写 56 字节 → `mode="U:240x320p-60\n"` → `virtual_size="240,960\n"`。

**坑**：该驱动 store 回调返回 0 而不是 count，`write()` 返回 0 但内容已生效。必须容忍 0（`sysWrite(path, b, zeroOK=true)`），否则会误判失败而跳过后续 `mode` 写入。

### 5.2 开混合

顺序：`alpha(1,255)` → `key(1,0)` → 校验 `com & 15 == 14` → `blank(0)` → 校验 `com & 15 == 15`。日志标记 `BLEND_ARMED` / `BLEND_ENABLED`。

### 5.3 上屏：必须 `pwrite`，不能用 mmap 写

**这是最隐蔽的一个坑。**

现象：进程内 `back` 缓冲与 `fb` 映射逐点比对完全一致（`eq=true mism=0`），但 `dd if=/dev/fb1` 读到的还是旧内容；画面"很久才变一次，还落后整整一首歌"。

结论：**进程内一致 ≠ 写进显存**。fb1 是 uncached 映射（逐字节读写 ≈ 每次一次总线事务），`copy()` 到映射区不会立刻反映到扫描输出。

修复：`copy(d.fb[...], d.back[...])` → `syscall.Pwrite(d.fd, d.back[off:end], off)`，由驱动落进真实显存。改完立刻同步。

### 5.4 解码直写目标带（省掉一整趟缩放）

LZ4 的 match **永远引用已输出区域**，所以只要 literal 写入时修零，整块输出必然已修零——可以省掉独立修零扫描。

命中条件：`w==1920 && h==midH && stride==3840 && rawlen==midH*stride` → 直接 `lz4DecodeFix(comp, d.back[bandOff:bandEnd])`。`DIRECT_VERIFY diff_bytes=0` 证明与「解压+缩放」逐字节一致。

### 5.5 双核流水线

每帧原本串行三段：read 1.2ms + LZ4 解码 2.18MB **24.6ms** + 整带写 fb **21.9ms** ≈ 48ms（20fps）。

改成「解码 goroutine + 单 worker 写 fb」：20.3 → **22.9fps**（两个核抢内存带宽，各自慢 10–15%，净收益 13%）。

**写 fb 必须单 worker 串行**，否则会撕裂。

### 5.6 上下条刷新间隔

每次整幅 `flush()`（把 fb0 的上下条 + 中间带一起刷）要 15–20ms。250ms 一次等于**每 5 帧白吃一帧**。

`ICBANDS 250 → 1200ms`：22.9 → **27fps**，是最大的一笔优化。已写成 `startcast.sh` 默认值。

### 5.7 已验证不是瓶颈的东西

| 项 | 验证方式 | 结论 |
|---|---|---|
| 每帧 `FBIOBLANK(0)` | `ICSUBMIT=none` 关掉 | 帧率一点没变，**别再往这优化** |
| `FBIOPAN_DISPLAY` | 恒 `EINVAL` | virtual==visible，无可 pan 偏移 |
| 每帧 `FBIOPUT_VSCREENINFO` | 实测 | 无效 |
| 仪表侧做合成（渐变/卡片/bands） | 实测 | 只有 8.3fps，**不该在仪表合成** |

| 坑 | 现象 | 对策 |
|---|---|---|
| `pkill -f <类名>` 杀自己 | 命令行含该串，pkill 按 PID 顺序先杀自己 → 「重启成功但旧进程还在」 | `killvds.sh` 只杀 `/proc/pid/cmdline` 以 `app_process` 开头的 |

| 僵尸/fd 泄漏 | screencap 跑几十帧后 `error=13` | 三个管道逐个 close + `waitFor()` |

### H. 性能

| 坑 | 现象 | 对策 |
|---|---|---|
| 采集被发送拖死 | TCP 满 → write 阻塞 → buffer 占满 → 冻屏 | 单槽队列 + 独立 tx 线程 |

| 逐字节读写 uncached fb | 每次约 180ns 总线事务 | 整行 copy 到 cache 内 rowbuf，按 u32/u16 处理，最后一次提交 |
| 重叠匹配改 memmove | 小长度调用开销盖过收益，decode 15.8→22.6ms | 回滚为逐字节循环 |
| 每帧整幅 flush | 15–20ms | `ICBANDS=1200` |

#### 9.4.1 `paint`：分区绘制

验证「自己画的 UI 面板」和「原厂画面透出」能不能同屏共存。不经过投屏链路，纯测 fb1 合成能力。

```
icrecv paint <hold> <x,y,w,h,color>...
  color = hole       纯 0x0000，色键透明，透出 fb0
        | #RRGGBB    按 RGB888 给，内部转 565
        | RRRR       直接当 RGB565（0001 = 近黑，不透明）
```

**整屏默认就是 `hole`**，只画你给的矩形，其余全部透出原厂。所以：

- 想验证挖洞 → 画一两个色块，看其余区域是不是原厂画面
- 想验证全屏替换 → 画一条 `0,0,1920,720,#101820` 全部盖住

实测日志（三块对比）：

```
RECT 100,100 400x200 color=0001 0001
RECT 700,100 400x200 HOLE show-fb0
RECT 1300,100 400x200 color=051F #00A0FF
BLEND_ARMED  com=14 gw=0xff000000
BLEND_ENABLED com=15 gw=0xff000000
PAINT rects=3 hole_rect=1 selfdraw=11.6% seethrough=88.4%
RESTORED blank=4 / RESTORE_OK
```

三个必守的约定：

1. **`#000000` 会被转成 `0x0000`，等于 hole**。需要"纯黑"请直接写 `0001`；
2. 结束自动 `restore`，中途要中断就 `kill` 后再跑一次 `restore`；
3. `icrun.py` 的等待秒数必须**大于** hold，否则命令跑了但拿不到回包（表现为输出为空）。

## 13. 应用化：能不能打包成一个 App 装车上

**结论先说**：纯 APK 装不出来；能做的是「APK 壳 + 特权助手」，或者走 Shizuku（车友那个歌词 APK 就这么干的）。

### 13.1 纯 APK 卡在哪三道墙

| 要调的能力 | 需要的权限 | 性质 |
|---|---|---|
| `SurfaceControl.captureDisplay` | `READ_FRAME_BUFFER` | signature / privileged |
| `VirtualDisplay.createPublicVirtualDisplay` | `CREATE_VIRTUAL_DISPLAY` | signature |
| 搬窗口（等价 `am display move-stack`） | `MANAGE_ACTIVITY_TASKS` / `INTERNAL_SYSTEM_WINDOW` | signature |

全是 hidden API + 系统签名。有实测证据：**同一个 dex，售后域 `u:r:xpaftersalesd:s0` 下 330 次后 captureDisplay 恒返回 null，shell 域下 1500 次零失败**——SELinux 域一变结果就变，普通 app 域比售后域还窄。

### 13.2 能搬进 APK 的部分

- 与仪表的所有通信：`30510` 控制口 + `5560` 发帧口。**只要有 INTERNET 权限就行**——30510 无鉴权，这也是这东西的安全软肋。
- UI、开关、裁切区配置、fps 面板、状态显示。
- **采集搬不进去**。这是唯一搬不动的部分。

### 13.3 三条可行路线

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. Shizuku** | APK 普通安装，靠 Shizuku 提到 shell uid 2000 跑特权代码。shell 域正好是验证过能 `captureDisplay` 的域 | 要装 Shizuku 常驻；每次重启要重新激活（无线调试 adb）；车机能否稳定起要看 adb 5050 重启后是否还在 |
| **B. APK + 现有 app_process 助手**（推荐先做） | APK 只当遥控器：`30510` 管仪表、本地 socket/文件管车机侧的 `app_process`。采集链路一行不改 | 车机侧那半个还得靠 adb 起；要「开机就有」得解决自启 |
| **C. 特权 APK** | 塞进 `/system/priv-app` 或拿系统签名 | 需要签名密钥或能写分区，**目前没有** |

### 13.4 关键区分：两条完全不同的技术路线

- **车友（合法通道）**：车机 APK → 伪造 MediaSession → 原厂 CarService → 仪表**原生媒体卡片**。不碰像素，位置字号全由固件决定，但绝对安全。
- **本项目（越界通道）**：车机采集 → TCP 5560 → 仪表侧 Go 进程**直接写 fb1**。像素级自由，但绕开了原厂显示通道——这就是 §1.3 那堆风险的来源。

想做成「能长期用、敢在车上装」的东西，A/B 只是工程问题；真正要权衡的是**要不要继续走越界通道**。
