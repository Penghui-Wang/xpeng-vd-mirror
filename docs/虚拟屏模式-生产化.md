# 虚拟屏模式（`--mode vd`）生产化

日期：2026-11-02
分支：`exp/vd-capture-token`
代码：`asx/src/com/probe/asx/VdSend.java`

## 一、它解决什么问题

主屏模式（`--mode main`）抓的是**主屏合成结果**，所以车机屏幕上必须看得到目标窗口。
一旦把 QQ音乐 最小化、或者用导航盖住它，仪表中间带就跟着变成被盖住的样子。

虚拟屏模式把 QQ音乐 的窗口搬到一块**独立的虚拟屏**上，再从那块屏采集：

- 车机屏的右栏会露出底层的地图（导航），仪表照旧显示音乐
- 车机随便切界面，投屏内容不受影响

代价：车机屏幕上就没有 QQ 了，用户在车上点不到它（仪表端只投画面，不带触摸）。

## 二、用法

```bash
bash tools/startcast.sh vd      # 虚拟屏模式
bash tools/startcast.sh         # 主屏模式（默认，行为同以前）
bash tools/stopcast.sh          # 停（会等窗口搬回主屏）
bash tools/status.sh            # 看状态（含虚拟屏数与窗口位置）
```

单跑车机端：

```bash
# 启动
adb shell "CLASSPATH=/data/local/tmp/vd.dex setsid app_process /system/bin \
  com.probe.asx.VdSend --child --mode vd 1920 568 30"

# 换目标 app
... --mode vd --pkg com.tencent.qqmusicpad

# 只做恢复（kill -9 之后残留用）
adb shell "CLASSPATH=/data/local/tmp/vd.dex app_process /system/bin \
  com.probe.asx.VdSend --restore --pkg com.tencent.qqmusicpad"
```

## 三、实现：五个必要条件

DMS 建的虚拟屏**不把 display token 暴露给客户端**（`VirtualDisplay.mToken` 是
`IVirtualDisplayCallback`，`DisplayCaptureArgs.Builder` 只有 `setDisplayToken`、
没有 `setDisplayId`），所以不能直接对虚拟屏 capture。绕法是自建一个
**shadow display**，把它的 layerStack 指向虚拟屏，再对 shadow 的 token 抓。

这条链上每一步都是硬条件，缺一个就恒返回 null：

```java
// 1) 用 com.android.shell 的包上下文建屏（app_process 的 uid=2000，
//    用系统上下文会被 DMS 拒绝：packageName must match the calling uid）
Context pkg = sys.createPackageContext("com.android.shell", CONTEXT_IGNORE_SECURITY);
DisplayManager dm = pkg.getSystemService(DISPLAY_SERVICE);

// 2) 虚拟屏必须有输出面，否则 shadow 也没法合成（--nosurf 实测 360 次全 null）
ImageReader ir = ImageReader.newInstance(2400, 1200, RGBA_8888, 1);
VirtualDisplay vd = dm.createVirtualDisplay("asxvd", 2400, 1200, 160, ir.getSurface(), 0x9);

// 3) 建 shadow display
IBinder tok = SurfaceControl.createDisplay("asxvdshadow", false);

// 4) 必须用显式 Transaction：静态 setDisplaySurface() 依赖全局 transaction，
//    在 app_process 里是 null，直接 NPE
SurfaceControl.Transaction tx = new SurfaceControl.Transaction();
tx.setDisplaySurface(tok, shadowReader.getSurface());
tx.setDisplayProjection(tok, 0, new Rect(0,0,2400,1200), new Rect(0,0,2400,1200));
tx.setDisplayLayerStack(tok, vdDisplayId);   // 关键：共享虚拟屏的图层
tx.apply();

// 5) 尺寸必须与虚拟屏一致 —— 缩放投影在本机不生效，shadow 只做 1:1 裁切
```

裁剪和缩放仍由 `DisplayCaptureArgs.setSourceCrop + setSize` 完成，
所以两个模式共用同一套 `vdcrop.txt` 坐标，切模式不用改参数。

## 四、今天新踩的三个坑

### 1. 搬回主屏会被重新布局成全屏

**先说小鹏的分屏规则**（车主确认）：屏幕被分成三段——

- 地图、系统音乐等少数应用可以占 **1/3 屏**（左栏，约 `[120,0][946,1080]`）
- 其他应用一律占 **2/3 屏**（右栏，`[960,0][2400,1080]`，宽 1440）
- 不管在哪个区，**拖动窗口边界都能拖成全屏**

所以 QQ音乐 的正常状态是 `[960,0][2400,1080]`，不是全屏。

问题出在 `am display move-stack <task> 0`：窗口离开虚拟屏后，系统按 fullscreen
重建，bounds 落到 `[0,0][2400,1200]`。此时裁切区 960,345,1440,426 落在全屏画面
中部的大片空白上，压缩后只剩 **8.5KB**（正常 350KB），看起来"还在跑"，其实全是纯色。

修正：搬回主屏后必须重新走一次分屏布局：

```bash
am start -n <component> --windowingMode 5
```

这一条就能把窗口恢复到 2/3 区的 `[960,0][2400,1080]`，不需要 `am task resize`。
代码里做成 `restoreRightPane()`，搬完用 `boundsOk()` 校验（x≈960、宽≈1440），
不合格才 resize 兜底。

从 display 0 直接搬到虚拟屏时 bounds **不会**变，所以正常流程不需要这一步。

> 反过来也成立：如果用户手动把 QQ 拖成全屏再去投屏，裁切区取到的就是全屏画面的
> 中间一块（内容还是 QQ，但构图不同）。要投全屏就改 `vdcrop.txt` 到 `0,0,2400,1200`。

### 2. `app_process` 下的 ART 收到 SIGTERM 不执行 shutdown hook

`Runtime.getRuntime().addShutdownHook(...)` 注册的恢复逻辑**一行都没跑** ——
`vdsend.log` 里连 `RESTORE start` 都没有。进程被 TERM 后直接终止，
虚拟屏随之销毁，系统自动把 task 迁回主屏（这也是为什么窗口"看起来恢复了"，
但其实是全屏）。

修正：恢复不依赖被杀的进程，改成 `killvds.sh` 里起一个**独立进程**做幂等恢复：

```sh
kill -TERM <pid>          # 停采集
sleep 2                   # 等虚拟屏销毁、系统迁移 task
CLASSPATH=/data/local/tmp/vd.dex app_process /system/bin \
  com.probe.asx.VdSend --restore --pkg com.tencent.qqmusicpad
```

`--restore` 是幂等的：窗口已在右栏就什么都不做（否则会把用户正在用的导航拉到前台），
检测到 display≠0 或 bounds 不对才修。

### 3. Windows 下写的脚本推上车机后语法错

`killvds.sh[15]: : inaccessible or not found` / `syntax error: unexpected 'do\r'` ——
CRLF 换行。toybox sh 不认。推送前统一转 LF：

```bash
python -c "import io,glob;[io.open(p,'wb').write(io.open(p,'rb').read().replace(b'\r\n',b'\n')) for p in glob.glob('tools/**/*.sh',recursive=True)]"
```

## 五、实测数据

车机 8295 / Android 12，仪表 i.MX6 双核，同一网段直连。

### 同一个画面，两种模式对照（QQ 播放页）

| 模式 | 车机采集 | 车机发送 | 仪表接收 | 仪表分段 |
|---|---|---|---|---|
| `--mode main`（主屏） | 30fps，procMs 11 | 30fps，7.1–8.0MB/s | **17.2–17.3fps** | read 11.6–11.9ms + dec 42–44ms |
| `--mode vd`（虚拟屏） | 30fps，procMs 10–13 | 30fps，7.0–7.6MB/s | **18.3–19.4fps** | read 8.0ms + dec 41–44ms |

**虚拟屏模式不但没有额外开销，还略快一点**（read 从 11.9ms 降到 8.0ms）——
主屏那边图层更多（地图、状态栏、左栏播放器都要一起合），capture 本身就更贵。

### 帧率随画面复杂度的变化

| 画面 | payload/帧 | 仪表解码 | 仪表帧率 |
|---|---|---|---|
| 简单画面（大面积纯色，"米店"播放页） | 82KB | 21–28ms | 26–27fps |
| QQ 首页（多彩歌单卡片） | 390–500KB | 40–44ms | 18.5–21fps |

仪表是双核，`loadavg 4.7` 本来就超载。解码和写 fb 已经排满，
payload 一大就掉帧——**这是仪表算力的天花板，与投屏模式无关**。

## 六、限制与后续

1. **车机上摸不到 QQ 了**。它被搬到虚拟屏，中控右栏露出底层地图。
   要恢复交互只能：切回 `--mode main`，或者以后做触摸透传。
2. **帧率受画面复杂度影响大**（19–27fps）。想稳住 30 需要脏块协议：
   按 16 行 strip 比对前后帧，只传变化的条，带宽和解码同时砍掉。
   这是两侧都要改的活（Java 发送端 + Go 接收端）。
3. **只支持一个目标窗口**。换 app 用 `--pkg`，但同时投两个需要两套虚拟屏。
4. **异常退出（kill -9）会留下全屏窗口**，靠 `stopcast.sh` 里的 `--restore` 兜底，
   或手动跑 `VdSend --restore`。
