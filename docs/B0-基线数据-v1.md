# B0 基线数据 v1（2026-11-05 驻车实测）

> 口径：同一 APK（`com.xiaopeng.vdcast` 2.0 / versionCode 1）、同一车机（8295 / Android 12）、
> 同一仪表（i.MX6 / 996MHz，散热 49℃，未降频）、驻车未导航。
> 时间一律取 `logcat -v threadtime` 的毫秒时间戳；应用自身日志已带 `HH:mm:ss.SSS`（PERF-00）。
> 原始产物：`docs/materials/b0/round{1..5}.*`（不入库，本地留档）。

---

## 1. 结论先看这四条

1. **冷启动已经很快，没有优化空间**：155–165ms 到首帧，目标值再怎么定都够。
2. **投屏启动 4.3–8.2s，是操作链里最慢的一环**；慢在两处固定的仪表 RPC（各约 1.5–1.9s）和「拉起目标应用」（1.2s）。
3. **60fps 不是链路属性，是画面面积的属性**：550×384 = 61.8fps，1920×568 = 30–39fps。
   仪表端解码 ≈ **20–24 ns/px**，1.09M 像素根本进不了 16.7ms 的预算。`docs/帧率优化记录.md` 里的
   58.6–59.9fps 是在 **550×384** 上测的，不代表满宽横带。
4. **一个真 bug**：自定义矩形用过之后再切回「默认满宽横带」（不重启应用），`outW/outH` 不回落，
   发送/接收仍是上次的 550×384，却往 1920×568 的带里画 —— draw 从 2ms 涨到 21.5ms、帧率 27fps。

## 2. 冷启动（PERF-01 / PERF-02 / PERF-03 / M3）

`am start -W` 五轮，每轮先 `am force-stop` + 等 3s。

| 轮次 | LaunchState | TotalTime | WaitTime |
|---|---|---|---|
| 1 | COLD | 156 ms | 158 ms |
| 2 | COLD | 158 ms | 161 ms |
| 3 | COLD | 165 ms | 168 ms |
| 4 | COLD | 157 ms | 160 ms |
| 5 | COLD | 155 ms | 158 ms |
| **中位数** | — | **157 ms** | **160 ms** |
| P90 | — | 165 ms | 168 ms |

- **PERF-01 冷启动 → 首帧**：**157 ms（中位数）/ 165 ms（P90）**。
- **PERF-02 冷启动 → 首个按钮可点**：与首帧同帧（整屏是代码直建的单层 `LinearLayout`，按钮首帧即存在），
  取同一组数；本轮**未做 60fps 抽帧**（本机无 ffmpeg，见 §7）。
- **PERF-03 点连接 → 已连接**：五轮 5 / 5 / 5 / 5 / 6 ms，均命中「token 20B 用 raw 签名（第 1/3 种）」。
  远优于 0.8s 目标，**这项不需要优化**。
- **M3 `logcat -b events`**：本 ROM **不产生 `am_activity_launch_time`**（车机侧全缓冲区 `grep -c` = 0，
  耗时 2.9s，不是采集被截断）。可用的只有 `am_proc_start`：进程起 → 应用打出第一行日志约 **56ms**。
  **结论：M3 用 `am start -W` 的 TotalTime/WaitTime 作口径，不再指望 events 缓冲区。**

## 3. 投屏启停（PERF-04 / PERF-06 / PERF-11）

### 3.1 启动分解（第一次，冷进程 + 目标应用未运行）

`遥控 → vd` 14:17:43.821 → `就绪` 14:17:52.064 = **8.24s**

| 阶段 | 耗时 | 说明 |
|---|---|---|
| [0/8] 探活 + 写 vdcrop.txt | 40 ms | 两次 adb exec |
| [1/8] 推 dex + killvds | 26 ms | 77KB，dex 未被跳过（进程首启） |
| [2/8] 停旧发送端 | 240 ms | `killvds stop`，无旧进程 |
| [3/8] 确保目标应用有窗口 | **1.20 s** | 目标应用没在跑，`am start` 拉起 + 等窗口 |
| [4/8] 校验仪表端二进制 | **1.88 s** | 一次 Icrpc（md5 比对）+ 命中跳过推送 |
| [5/8] 起仪表接收端 | 0.49 s | 1–2 次 Icrpc |
| [6/8] 起车机发送端 | **1.92 s** | 等 `capture ready` |
| [7/8] 等端到端出帧 | **2.37 s** | 轮询仪表日志到 `frames=` |
| [8/8] 健康检查 | 109 ms | 两次 adb exec |

### 3.2 同进程二次启动（工具已同步、目标应用已在跑）

36.216 → 40.504 = **4.29s**，比首次少 3.95s，差值正好落在「拉起应用 1.2s + 校验二进制 1.88s + 多出的停旧 0.9s」。

- **PERF-04 基线：首次 8.24s / 二次 4.29s**（原目标 ≤4s，二次启动刚好压线）。
- **PERF-05 换应用重启：本轮未测**。原因见 §7：旧应用窗口可能被留在已销毁的虚拟屏上，
  属于会伤车的实验，留到 B3 做「换应用」功能时一起测。

### 3.3 裁切热生效（PERF-06）

设备侧 `/proc/uptime` 打点，`am start --es crop … --es act crop` 到 `vdsend.log` 出现 `crop reload 970,345,550,384`：
**310 ms**（含 `am start` 传递，应用自身下发只占 20ms）。

- 目标 ≤0.8s，**基线 0.31s，已达标**。
- 附带发现：`am start --es act crop 1,2,3,4` 的写法会把 `1,2,3,4` 当 data URI 吃掉，
  `crop` extra 丢失、沿用旧值（第一次测出来「裁切已设为 960,…」就是这个原因）。
  正确写法：`--es crop 1,2,3,4 --es act crop`。**这条要写进遥控入口说明（UX-11）。**

### 3.4 裁切页首帧（PERF-07）

`取当前画面作底图…` → `已取到 391 KB` = **360 ms**（虚拟屏 display 72 截图），
加上 CropActivity 起页约 200ms → **≈0.55s 能看到底图**。

### 3.5 停止（PERF-11）

三次实测：**4.97s / 4.99s / 约 5.0s**，其中 [1/3] `killvds stop` 占 4.35s，[2/3]、[3/3] 各约 0.26s。
三次均 `RESTORE_OK`、残留进程 0、残留虚拟屏 0。

- 目标 ≤4s，**基线 5.0s，超 1s**，且 4.35s 全花在 `killvds stop` 上 —— B5 有明确抓手（等 TERM 不等 KILL）。
- **退出（应用级）尚无穷举，未测**：`UI-08 / UX-05` 还没做，没有退出入口。

## 5. 帧率基线（M8）——本节是本次最重要的发现

同一时刻两端同时采样，`vdsend.log` 取 `fps=`，仪表 `/tmp/icrecv.log` 取 `frames=`：

| 配置 | 车机 | 仪表 | 仪表单帧分解 |
|---|---|---|---|
| **550×384**（crect 750,220） | fps=61，sent 稳定 +61/s | **61.7–61.8 fps**，total 14.4–17.9ms | read 4.7–7.7 / dec 3.9–4.4 / draw 1.9–3.4 / flush 3.0–3.3 |
| **1920×568 原生**（crop 0,0,1920,568，1:1 无缩放） | fps=62，procMs=9 | **30.2 fps（首帧）→ 38.9–39.0 fps（稳态）** | read 2.0–5.6 / **dec 22.0–26.6** |
| **1920×568 带 + 发送 550×384**（见 §6 的 bug） | fps=62 | **27–28.9 fps** | read 2.2–396(!) / dec 3.4 / **draw 21.5 / flush 9.5** |

**解读**

- 仪表解码成本**与像素数成正比**：1,090,560px ÷ 22ms ≈ **50 Mpx/s（20 ns/px）**；26.6ms 时约 41 Mpx/s。
- 60Hz 预算 16.7ms，扣掉 read/draw/flush 约 5–6ms，**dec 只剩 10–11ms → 面积上限约 45–55 万像素**。
  换算：960×500（48 万）勉强、1280×400（51 万）勉强、**1920×568（109 万）必然只有 30 帧**。
- **所以「仪表 58.6–59.9fps 已贴 60Hz 上限」这个说法只在 550×384 上成立**。
  满宽横带是 1.09M 像素，物理上到不了 60。这不是回退，是从来没在满宽上测过。
- 直接后果两条：
  1. B5 的硬门槛「仪表 ≥58fps」**必须带面积条件**，否则永远判不合格；
  2. 默认 `crect` 就是满宽横带（`0,72,1920,568`），**用户开箱即用拿到的是 30 帧**。
     真要 60 帧，得让用户选一块小区域 —— 这是产品口径问题，需要你定（见 §8 Q1）。
     > **2026-11-05 16:00 已按 B 口径解决**：默认改成 `352,180,1216,360`（43.8 万像素），
     > 上面这条「开箱即用拿到 30 帧」不再成立。满宽横带仍可手动选，但不推荐。详见 §8 Q1。

## 6. 顺带测出来的一个真 bug（UX-15，新增）

**现象**：先投过自定义矩形（`crect 750,220,550,384`），再改回默认满宽横带（`crect 0,72,1920,568`）
并重启投屏（**不重启应用**），实际发出的是：

```
[0/8] ok (mode=vd, 目标=…, 550x384, 60fps)     ← 尺寸还是上次的
[5/8] 起仪表接收端（投屏区 满宽横带 y=72..640）  ← 矩形已经是默认值
仪表: recv 550x384，DST 0,72 1920x568
```

**根因**：`VdCtl.start()` 只在 `cCustom == true` 的分支里把 `outW/outH` 同步成 `cW/cH`；
切回 `cCustom == false` 时没有任何一行把 `outW/outH` 恢复成 1920×568，而 `Cfg` 对象是进程级的，
于是沿用上一次的自定义值。

**后果**：550×384 的帧被画进 1920×568 的带里 —— 仪表 `draw` 从 2ms 涨到 21.5ms、`flush` 涨到 9.5ms、
总帧时间 36.8ms、帧率掉到 27fps，画面还是拉伸的。**这就是 UI-13 那条「先定矩形再框选会变形」的同一族问题，
但更严重：这次是发送/接收尺寸和落屏矩形三者不一致。**

**与已有需求的关系**：归入 `UI-13` 的修复范围（锁比例用 crect 算），另起 `UX-15` 跟踪「参数回落」，
和 `UX-03`（热生效 / 需重启分级）同批做。

## 8. 需要你定的两件事

**Q1（重要）60 帧的目标区域怎么定？—— 已定案：B（2026-11-05 16:00 改判）**

现状：默认满宽横带 1920×568 → 30–39fps；550×384 → 61.8fps。

- ~~A. 承认物理上限：硬门槛改成「按面积分档」（≤50 万像素 ≥58fps；>50 万像素只保证 ≥30fps），UI 上标注实际帧率。~~
- **B. 坚持 60 帧：默认矩形收窄。← 采纳**
- 原倾向 A。

**为什么从 A 改回 B**：仪表是**安全件**，长期被投屏占满本身就不该是默认行为。A 口径虽然诚实，但它把「占满仪表」留成了出厂状态，只靠面板上的一行字提醒 —— 对安全件来说，默认值比提示更重要。

**落地值**：默认矩形 `352,180,1216,360` = **43.8 万像素**，居中于 1920×720。

| 项 | 值 | 理由 |
|---|---|---|
| 面积 | 437,760（43.8 万） | 按解码预算推算的面积上限约 45~55 万，取在 45 万一线之下 |
| 比例 | 1216/360 = 3.3802 | 与默认 `crop` 1440×426（3.3803）差 0.07%，不会变形 |
| 位置 | x=352, y=180 | 严格居中：352×2+1216=1920、180×2+360=720；不压上下告警带（72/80） |
| 缩放 | 0.845× | 原满宽横带是 1.33× 放大，所以画质反而更锐 |

**不承诺帧率（16:12 车主明确）**：面板与日志只说面积，不写「可跑满 60 帧」这类档位。原因是**帧率还受画面复杂度影响** —— 静态画面和高动态画面不是一个成本，写死档位等于给自己挖坑。真帧率一律以三层小灯的实测值为准。

先取过 `1298×384`（49.8 万），但那个值贴着预算上限、几乎没有余量，于是又降了一档到 1216×360。

**全屏仍可做，但不再默认**：手动填 `0,72,1920,568` 或让 `cCustom=false` 都能回到满宽横带；此时面板提示会变成「⚠ 仪表为安全件，不建议全屏投放……面积越大帧率越容易掉」。判据、默认值、提示文案由 `adbprobe/test/CfgTest.java` 的 27 条断言钉住。

**Q2 `killvds stop` 的 4.35s 要不要在 B5 动？**
它是「停投屏 5s」的全部成本，改法是把「等 TERM 让窗口搬回去」的固定等待改成轮询。
不属于投屏帧率，属于操作速度，**动它风险低**（只影响停止路径）。默认按「动」。

## 9. 复现方式

```bash
# 冷启动五轮（一次一轮跑，本机沙箱对长命令有超时）
bash tools/bench/b0_coldstart.sh 1 1
bash tools/bench/b0_coldstart.sh 1 2      # 依次到 5

# 连接耗时 / 启动 / 停止：全部从 logcat 的毫秒时间戳读
adb shell logcat -d -v threadtime -s ADBPROBE:I

# 两端帧率：车机看 vdsend.log，仪表走 30510
adb shell "grep 'fps=' /data/local/tmp/vdsend.log | tail -1"
python probe/icrpc.py "grep -E 'frames=' /tmp/icrecv.log | tail -2"

# 启动投屏（注意 --es 的 key 在前，且 act 必须最后给）
adb shell am start -n com.xiaopeng.vdcast/.MainActivity \
  --es pkg com.tencent.qqmusicpad --es crop 960,345,550,384 --es crect 750,220,550,384 --es act vd

# 停止
adb shell am start -n com.xiaopeng.vdcast/.MainActivity --es act stop
```

> 每次实验收尾必须确认三件事：`残留进程: 0`、`残留虚拟屏: 0`、仪表日志有 `RESTORE_OK`。
> 本轮 4 次启停全部满足，两端无残留（已核对 `ps`）。
