# 审计：adbprobe 四类改造（UI / 逻辑 / 速度 / ADB）

> 范围：只审计，不改代码。依据 = 仓库现有源码与文档，未假设看不到的实现。
> 结论按「现象 → 影响 → 模块 → 初步判断」组织，ID 可直接作为后续提交/验收的锚点。

---

## 0. 先确认的三条边界

| 项 | 结论 | 依据 |
|---|---|---|
| UI 改造范围 | 只在 `adbprobe/`（含 `assets/`）。`tools/` 只允许改运维脚本 | 现有 UI 全部代码构建，无 res/ 无第三方库 |
| compose 命令行签名 | **不改**。现状 `VdCtl.startReceiver()` 已按冻结签名调用：`compose <port> <hold> <top> <bot> 0 [x y w h]`，自定义矩形时才追加 4 个参数 | `VdCtl.java:500`、`icrecv2/main.go:2044` |
| `asx/`、`icrecv2/` | 本轮不动。UI/逻辑/速度的诉求都能在 adbprobe 侧闭环（见 §4 的「不碰 asx 的做法」） | — |

一个例外要先说清楚：**「预览放在启动投屏之前」如果要求实时 VD 画面，最小改动点在 `asx/`（VdSend 需要「只采不发」模式）**。不碰 asx 的替代路径是「静态预演」，详见 UX-02。

### 1.2 跨端调用关系（实际数据流）

```
MainActivity
├─ Adb.connect(127.0.0.1:5050 或本机网卡IP)  ──► 车机 adbd（shell 域 u:r:shell:s0）
├─ VdCtl.start()
│   ├─ adb push  assets/vd.dex      → /data/local/tmp/vd.dex
│   ├─ adb push  assets/killvds.sh  → /data/local/tmp/killvds.sh（与 tools/remote/killvds.sh 同源）
│   ├─ sh killvds.sh stop <pkg>     → TERM VdSend → app_process --restore 把窗口摆回右栏 → kill -9
│   ├─ ensureTargetApp()            → am stack list 解析 + monkey 拉起
│   ├─ ensureClusterBinary()        → Icrpc 探针 / md5 / relayToCluster(HTTP) → 仪表 /tmp/icrecv_dbg
│   ├─ startReceiver()              → Icrpc: 杀旧 + setsid ./icrecv_dbg compose …→ /tmp/icrecv.log
│   └─ startSender()                → CLASSPATH=vd.dex setsid app_process com.probe.asx.VdSend --child …
├─ setCrop()  → echo x,y,w,h > /data/local/tmp/vdcrop.txt（VdSend 每 15 帧比对，热生效）
└─ snapshot() → screencap [-d <vd display>] → adb pull PNG → CropActivity 底图
PreviewActivity ←─ VdSend --preview 5570（127.0.0.1，未压缩 RGB565，ICF1 24B 头 + 裸像素）
仪表 icrecv_dbg compose ←─ 车机 5560（LZ4）→ pwrite /dev/fb1 目标矩形；矩形外 fb0 补回
```

### 1.3 与 `tools/` 的对应（PC 侧同源实现，改动时要同步认知，不必同步代码）

| APK 内 | PC 脚本 | 说明 |
|---|---|---|
| `VdCtl.start()` | `tools/startcast.sh` | 脚本是 7 步版，APK 是 8 步版（多了健康检查合并往返） |
| `VdCtl.stop()` | `tools/stopcast.sh` | — |
| `VdCtl.status()` | `tools/status.sh` | — |
| `Adb.connect` 重连 | `tools/adb.sh` | 脚本是「每次调用前 start-server + connect + 5 轮重试」；APK 内没有等价重试壳 |
| `relayToCluster()` | `tools/ideploy.sh` / `ifetch.sh` | 都走「车机起 nc HTTP + 仪表 wget」 |
| `pushDex` / `adb push` | `tools/push.sh`、`probe/pushmulti.py` | 仪表侧 nc 单连接 64KB 上限，`pushmulti` 按 60000B 分块并逐块校验 |
| 安装 | `tools/installapk.sh` | 图形安装器 + 键盘导航，`lastUpdateTime` 判定成功 |

### 1.4 三个「看起来能动、其实不能动」的点

1. `compose` 的 `cards=0` 与位置参数顺序：车上 APK 已固化，改了就得连 APK 一起换（README §6）。
2. `Adb.send()` 里 `data_check` 必须为 0、`SIGN_MODES` 的 `raw` 必须排第一：这台 ROM 的非标准 adbd 依赖它（`APK控制器-v0.2.md` §1）。
3. `killvds.sh` 必须按 `/proc/<pid>/cmdline` 以 `app_process` 开头匹配、且调用方命令行不能出现类名字面串：否则会杀到自己（注释里两个真实事故）。

## 2. ID 化需求清单

### 2.1 UI-*（对象：adbprobe 界面）

| ID | 现象 | 影响 | 所属模块 | 初步判断 |
|---|---|---|---|---|
| UI-01 | 选应用是 `AlertDialog` 单列纯文字，无图标、无搜索、无「不可投」标记 | 与车辆应用列表不一致；包名难认；列表里混着无 launcher 入口的应用 | `MainActivity.pickApp` + `VdCtl.candidateApps` | 新建独立选择页：网格/列表 + 图标 + 应用名 + 运行中角标；`PackageManager` 取 icon/label，加内存缓存；过滤无 launcher intent 的包 |
| UI-02 | 裁切底图来源不确定：无 VD 时截主屏，有 VD 时 `screencap -d` | 框出来的区域可能不是实际投出的画面（用户诉求 2） | `VdCtl.snapshot` + `CropActivity` | 底图按优先级取「VD 屏 → 目标应用窗口截图 → 主屏」，页面上角标写明来源；取不到 VD 时提示「先启动投屏/预演再框选」 |
| UI-03 | 预览页只有投屏区一块，黑色背景铺满全屏 | 看不出贴在仪表哪个位置、是否压到状态栏（诉求 3） | `PreviewActivity` | 本地合成：`assets/fb0_pre.png` 打底（1920×720）+ 在 `crect` 位置贴实时流；**不要**为了底图去 dump 仪表 fb1（会抢 icrecv CPU，见 R-01） |
| UI-04 | 主按钮写「启动 vd / 启动 main」 | 普通用户完全不理解（诉求 4） | `MainActivity.buildUi` | 主按钮改成「启动投屏」，`main/vd` 收进「高级」抽屉；默认 `vd`，并解释「切走车机屏不影响投屏」 |
| UI-05 | 界面没有「启动投屏」四个字 | 找不到主操作（诉求 5） | 同上 | 与 UI-04 合并做；主 CTA 只有一个，其余降级 |
| UI-06 | 工程风：输入框裸奔、按钮墙（启动 vd/main/停止/预览/状态/自检/连接 + 端口框）、日志占屏 | 观感差、误触（诉求 6） | `MainActivity` 全局 | 重排为「目标应用卡 → 区域卡 → 主 CTA → 折叠的高级/日志」；端口、自检、模式都收进高级 |
| UI-07 | 换应用后流程条「启动投屏/预览」不会变灰（诉求 7） | 状态说谎：界面显示已完成，实际跑的还是旧应用 | `MainActivity.step/refreshSteps`、`pickApp`、`startWith` | 根因是状态没有单一来源：`pkg/crop/crect` 变更都应让 step 4/5 失效。和 UX-03 同源 |
| UI-08 | 没有「退出应用」入口（诉求 8） | 只能系统杀，残留进程/虚拟屏 | `MainActivity` | 顶栏右侧或底栏危险区；行为见 UX-05 |
| UI-09 | 流程条顺序是 连接/选应用/裁切/仪表/启动/预览 | 与目标流程不符（诉求 UX-01/02） | `STEP_NAMES` 与各 `step()` 调用点 | 改为 连接 → 选应用 → 仪表区域 → 车机裁切 → 预演 → 启动；先定状态机再改文案，避免改两遍 |
| UI-10 | 状态只有一个 chip（待机/投屏中/启动失败） | 出问题只能翻日志定位 | `setState` | 三层小灯：adb / 发送端 / 接收端（+ 出帧率），失败的那层变红并给一句人话 |
| UI-11 | 日志区固定 122dp 常驻 | 工程味来源之一；普通用户用不到 | `buildUi` 日志卡 | 默认折叠成一行摘要，出错自动展开；保留长按/连点 5 次进「诊断模式」 |

| UI-13 | 裁切页「锁比例」用的是 `ctl.cfg().outW/outH`，而这两个值只在 `VdCtl.start()` 里才会被 `crect` 覆盖 | 用户先自定义仪表矩形、未启动就去框选 → 锁定的是旧的 1920/568，画面被拉伸或裁掉（代码上成立，待真机确认） | `CropActivity` + `VdCtl.Cfg` | 比例应在 `applyClusterCfg()` 时就同步到 `cfg.outW/outH`，或裁切页直接用 `crect` 算比例 |

### 2.2 UX-*（对象：启动到投屏的流程）

| ID | 现象 | 影响 | 模块 | 初步判断 |
|---|---|---|---|---|
| UX-01 | 仪表区域排在车机裁切之后（诉求 1） | 顺序反了：应该先定「贴在仪表哪里」，再按它的比例去车机取画面 | `STEP_NAMES` + 卡片顺序 | 调顺序即可，但要注意真正的约束：**仪表矩形决定发送尺寸**（`outW=cW`），所以先定仪表矩形在技术上更正确 |
| UX-02 | 预览在启动投屏之后；未启动时预览页只会无限重试「未连上发送端」（诉求 2） | 「先看效果再决定是否投」做不到 | `PreviewActivity` + `VdCtl` | 两段式：①「预演」= 静态合成（截当前 VD/主屏 + crect 摆位），零风险；②「实时」= 现有 5570 流。实时预演要 VdSend 先跑，若要「只采不发」必须动 asx → 见 §4 决策 |
| UX-03 | 换应用、改仪表矩形都不提示「需重启投屏才生效」；只有裁切是热生效 | 用户以为生效，实际跑旧参数（和 UI-07 同一根因） | `pickApp` / `onActivityResult` / `startWith` | 参数分两类：热生效（crop）/ 需重启（pkg、crect、mode）。改后者就把状态打回「待启动」并显示「需重新启动投屏」 |
| UX-04 | 关车/断电后重进，界面仍显示上次的完成态；残留进程、残留虚拟屏、仪表残留投屏区无人处理（诉求 3） | 第一次启动可能撞上「端口占用/残留进程」，表现为莫名其妙失败 | `MainActivity.onCreate` + `VdCtl` | 启动自检：`killvds.sh check`、`dumpsys display` 里 asxvd 计数、仪表 `ps icrecv_dbg`、`/tmp/icrecv.log` 是否有 RESTORE。有残留 → 顶部一条「检测到上次未正常结束」+ 一键清理 |
| UX-05 | 无退出应用；退出需要确认 + 等进程结束后再退（新增功能） | 直接 `finish()` 会留下 shell 域长驻进程 | `VdCtl.stop()` + `MainActivity` | 退出 = 复用 stop 链路 + 清理临时文件 + `adb.close()` + `finishAffinity()`；确认弹窗写明「将停止投屏并恢复仪表」；每步等待有上限（建议 8s 总预算），超时给出「哪些没停掉」而不是静默退出 |
| UX-06 | 一次投屏要点 3–4 个按钮；连接、拉起目标应用、启动是分散的 | 操作链路长 | 全流程 | 合并为一键：连接 → 自检 → 拉起/确认目标窗口 → 启动 → 等首帧；失败时停在具体那一步并给下一步动作 |
| UX-07 | 三类异常没有恢复路径：adb 掉线、仪表未开机/未监听、端口占用 | 用户只能重启 App | `ensureConn` / `startReceiver` / `VdCtl.start` | 分别给：自动重连 + 恢复上下文；仪表 ping/探测 + 明确提示；读 `/tmp/icrecv.log` 的 `listen:` 错误 → 提示端口占用并给「强制清理」 |
| UX-08 | 技术细节（fps、ms、进程数、md5）和用户状态混在一起 | 用户看不懂，工程师又嫌不够 | 状态区 | 分两层：用户级 4 态（未连接/待启动/投屏中/异常）+ 工程级折叠（现有 `status()` 原样塞进去） |
| UX-09 | 首次使用没有引导：授权弹窗、仪表要开机、必须驻车 | 第一次必然卡在授权 | 首启 | 3 步引导卡，只在首次显示；把「勾选一律允许」写清楚 |
| UX-10 | 面板在右半屏 freeform 运行，切走后投屏继续；行为没有定义 | 用户不知道切走会不会停 | 生命周期 | 建议：切后台不停投屏（这是它的价值），但状态栏/通知给一条常驻提示（需要通知权限，需确认是否接受） |
| UX-11 | 遥控入口 `am start --es act …` 是 PC 侧自动化依赖 | 改流程很容易破坏它 | `handleIntent` | 新增 UI 不改 `act` 语义；新动作只增不改；`act=preview` 之类保留兼容 |
| UX-12 | 停止/退出时若 `killvds --restore` 失败（窗口留在虚拟屏全屏）或仪表 restore 失败，界面只打日志 | 用户看到车机应用卡在全屏；仪表残留投屏区（安全相关） | `VdCtl.stop` | restore 幂等 + 二次尝试 + 明确红色结论；仪表侧以 `RESTORE_OK/RESTORED` 出现为准，未出现就不许显示「已停止」 |
| UX-13 | 目标应用是被 `monkey` 拉起的，退出时是否关闭没有定义 | 可能关掉用户正在用的音乐 App | `ensureTargetApp` | 建议只记录「本次由我们拉起」的包，退出时询问是否一并关闭；默认不关 |

### 2.3 PERF-*（对象：操作与部署，不含投屏帧率）

> 基线列标注来源：`docs` = v0.9 文档实测（3.4MB 二进制时代）；`待测` = 必须本轮采。

| ID | 指标 | 起止定义 | 采集方式 | 基线 | 目标（提案） |
|---|---|---|---|---|---|
| PERF-01 | APK 冷启动 | `am start` → 首帧可点 | `am start -W` 的 `TotalTime`；`logcat -b events` 的 `am_activity_launch_time` | 待测（文档的「冷启动 10s」含连接+投屏，不是纯启动） | ≤2.0s |
| PERF-02 | 面板可交互 | 冷启动 → 首个按钮可点 | `screenrecord --time-limit` + 逐帧 | 待测 | ≤2.5s |
| PERF-03 | 连接+认证（已授权） | 点连接 → `已连接` | logcat（需毫秒时间戳） | 待测 | ≤0.8s |
| PERF-04 | 启动投屏到首帧 | 点启动 → 两端各有 `fps=`/`frames=` | logcat + 仪表日志 | docs ≈6s | ≤4s |
| PERF-05 | 换应用重启投屏 | 点启动 → 新应用首帧 | 同上 | docs ≈11s（含 killvds 的 `sleep 2` + restore） | ≤6s |
| PERF-06 | 裁切生效 | 点确定 → 预览/仪表画面变 | screenrecord 60fps | docs 0.5s（热重载）+ 一次 RTT | ≤0.8s |
| PERF-07 | 裁切页首帧（底图可见） | 点框选 → 截图出现 | logcat + 录屏 | 待测（**风险点：整张 PNG 走 `adb pull`**） | ≤1.5s |
| PERF-08 | 预览首帧 | 进预览页 → 出画面 | logcat + 录屏 | 待测（连接超时 1200ms 起） | ≤1.2s |
| PERF-09 | 应用列表加载 | 点选择 → 列表可点 | logcat | 待测（`am stack list` + `pm list packages -3` 各 20s 超时） | ≤1.2s |
| PERF-10 | 仪表 RPC 单次固定成本 | 一条 Icrpc 调用往返 | logcat | docs ≈1.5s（哨兵优化后） | ≤0.8s 或合并调用 |
| PERF-11 | 停止 / 退出耗时 | 点停止/退出 → 进程与仪表都复原 | logcat + 仪表日志 | docs ≈5s（停止） | 停止 ≤4s；退出 ≤8s |

**测量方案（必须先做，别先改）**

1. 统一计时源：现在 `MainActivity.print()` 只到秒（`HH:mm:ss`），无法测 0.5s 级差异。第一步只加毫秒时间戳（不改行为），否则所有数据都是猜。
2. 取数规则：每指标 5 次，取中位数 + P90；同一 APK、同一驻车状态、屏幕常亮、连续两次测量间隔 ≥10s。
3. 三维基线：冷启 / 温启（进程在、投屏停）/ 投屏中；换应用、改矩形单独一档。
4. 感知延迟用 `screenrecord` 60fps 抽帧，不以日志为准（日志不含渲染）。
5. 每次测量记录：`versionCode`、`assets/vd.dex` 与 `icrecv_dbg` 的 md5、车机/仪表是否重启过（决定是否命中推送缓存）。
6. 失败样本要计入：`Adb` 掉线导致的中断会让 P90 完全失真，先修 ADB-02/03 再定稿 PERF 结论（见 §3 依赖）。

### 2.4 ADB-*

| ID | 现象 | 影响 | 模块 | 初步判断 |
|---|---|---|---|---|
| ADB-01 | 本应用连上 adbd 后，车机上其他含 adb 的应用都不能用了（README 记录的坑） | 与其他调试/工具类应用互斥 | `Adb` 连接策略 | 见 §5 根因假设；**先取证再改**，不要重写 ADB 模块 |
| ADB-02 | adbd/adb server 会被周期性回收；APK 内 `isConnected()` 只看 socket 状态，没有心跳 | socket 还「连着」但命令全超时，界面卡在忙碌 | `Adb.isConnected` / `ensureConn` | 加轻量探针（一次 `echo`，带超时）+ 失败即 `close()` 重连；不要在每次 `exec` 前都探（会翻倍往返） |
| ADB-03 | `readAll` 超时 → `close()` 整条连接，后续调用抛「未连接」；上层只打印，不重试 | 一次超时把整个会话打废 | `Adb.exec/readAll` | 区分「可重试（连接类）」与「不可重试（命令本身慢）」，前者自动重连一次 |
| ADB-04 | 首次授权要 3 轮握手，失败提示只有一行「三种签名都不被接受」 | 首次使用成功率低 | `Adb.tryOnce` | 保留现有「不重发公钥」的正确行为；UI 层给明确引导（UX-09） |
| ADB-05 | 连接目标枚举：127.0.0.1 → 本机各网卡 IP，端口手填 | 可能连到非预期设备；端口被占时无区分 | `ensureConn` | 连接结果里带 `endpoint` 与设备标识（`getprop ro.serialno`）核对 |
| ADB-06 | 每次 Icrpc 调用都 push 一个 `.adbprobe_fN.bin`；异常时残留 | `/data/local/tmp` 垃圾；每次都多一次 sync 往返 | `Icrpc.run` | 复用固定文件名 + 正常路径清理；失败也要清 |
| ADB-07 | push 只有 dex 校验大小、bin 校验 md5；killvds/脚本无校验 | 脚本半截落盘时行为怪异 | `Adb.push` / `VdCtl` | 关键文件落地后 `wc -c` 核对（成本一次 RTT） |
| ADB-08 | 单线程 worker + 全局 busy；relay 55s 期间无法取消 | 卡死感，且只能等 | `MainActivity.run` / `VdCtl.relayToCluster` | 长任务可中断（关 socket 即中断），UI 给取消按钮 |
| ADB-09 | 安装只能走图形安装器（`isPlatSigned:false`），三轮重试 | 迭代慢、易失败 | `tools/installapk.sh` | 不改 APK；补一条「安装后比对 APK md5/dex md5」的自动校验 |
| ADB-10 | `am stack list` 文本解析（`RootTask id=` / `taskId=…/…`） | 系统窗口格式一变就全失效，且失败是静默的（返回空列表） | `VdCtl.runningTasks` | 解析失败要区分「没任务」和「格式不认识」；加一条 `dumpsys activity activities` 兜底 |

## 5. ADB-01 根因假设（按可能性排序）

> 前提：本 APK **不会**启动 adbd，它只是客户端连 `127.0.0.1:5050`。所以「启用 adb server」如果指「开发者选项里打开 adb 调试」，那变量在 ROM；如果指「装了这个 APK 并点了连接」，才和本应用有关。这一点需要你确认（见 §8 Q1）。

| # | 假设 | 支持证据 | 反证/如何区分 | 可能性 |
|---|---|---|---|---|
| H1 | **adbd 只服务一条 transport**：新 host 连上会顶掉旧 host（或反之），两个「adb 宿主」天然互斥 | APK 会长期持有 socket（20s SO timeout，反复复用）；`Adb` 每 20s 级就有一条长命令在跑 | 让另一个应用先连、adbprobe 后连 → 若另一应用掉线；再让 adbprobe 主动 `close()`（退出应用）→ 另一应用恢复，则 H1 成立 | 40% |
| H2 | **授权键被覆盖**：该 ROM 的 adb_keys 只保留最后一把（或 vendor 自管白名单），adbprobe 的 key 把别家的顶掉 | APK 首次连接会提交公钥并「一律允许」；文档已证明这台 ROM 的 adbd 是非标准实现 | 另一应用重新弹授权窗 / 需重新点允许 → 支持 H2；看 `/data/misc/adb/adb_keys`（需 root）是否只剩一把 | 25% |
| H3 | **端口/服务冲突**：其他应用自带本地 adb server（5037）或依赖 `adb tcpip 5555`，与车机 adb 端口策略冲突 | 车机 adb 走非标准 5050，说明 ROM 改过调试口；其他应用可能硬编码 5555/5037 | 看另一应用报错是「connection refused」还是「unauthorized」；`netstat` 看 5037/5555 是否被占 | 15% |
| H4 | **fd/进程耗尽**：Icrpc 每次 push 帧 + setsid + nc，异常路径残留，把 adbd 的 fork/fd 吃满 | `Icrpc` 失败时会残留 `.adbprobe_fN.bin`；`relayToCluster` 起常驻 nc | 不操作、只挂着连接时另一应用是否正常；`ps -A \| wc -l`、`ls /proc/<adbd>/fd \| wc -l` | 12% |
| H5 | **ROM 策略**：检测到第三方 host（CNXN banner 的 `features=`）后降级/关闭调试口 | banner 是自定义串，可能触发厂商风控 | 换官方 adb 同时连，若官方也受限则是 ROM 策略 | 8% |

**最小复现（每组 1 分钟，按顺序做，任一步成立即可停止）**

1. E0：adbprobe 不启动（进程都不开），另一应用单独用 → 正常？不正常则与本应用无关，问题在 ROM/该应用。
2. E1：adbprobe 启动但不点连接，另一应用用 → 正常？正常则排除 H4/H5。
3. E2：adbprobe 点连接（保持前台），另一应用用 → 复现？记录另一应用的**具体报错文本**。
4. E3：adbprobe 退出应用（socket 关闭），另一应用立刻重试 → 恢复？恢复则指向 H1。
5. E4：另一应用重新授权一次后能否用 → 能用则指向 H2。
6. E5：PC 侧同时 `adb connect <车机>:5050` 做对照，看是不是「任意两个宿主都互斥」。

**日志增强（只加日志，不改逻辑）**

- APK 内：连接开始/成功/失败（含 `endpoint`、耗时 ms）、每次 `CNXN` 收到的 `arg1`、AUTH 用了哪种 `SIGN_MODES`、socket 被谁关闭（主动/超时/EOF）。
- 车机侧：`getprop | grep -i adb`、`ps -A | grep adbd`、`logcat -b all | grep -iE "adbd|adb_keys|auth"` 各抓一份，连接前后各一次。
- 判定口径统一：以「另一应用能否完成一次真实命令」为准，不看 `adb devices` 是否显示 online。

## 6. 风险点（重点看前 3 条）

| # | 风险 | 触发条件 | 后果 | 规避 |
|---|---|---|---|---|
| R-01 | **预览合成去 dump 仪表 fb1** | UI-03 若为了「真实底图」周期性抓仪表 | dump 与 icrecv 主循环同进程，可能把 59.9fps 拉到 50 以下 | 只用静态 `fb0_pre.png`；需刷新时限定「未投屏」状态下抓一次 |
| R-02 | **连接策略改动波及投屏链路** | B1 若改成「用完即断」但在 `start()` 中途断 | 发送端/接收端起不来，或起来后无人管 | 只在「批次任务边界」断开，不在 8 步流程中间断；每批回归一次 60fps |
| R-03 | **退出/停止顺序改错** | UX-05 若先杀 VdSend 再 restore，或 restore 未完成就 `finish()` | 车机应用卡在虚拟屏全屏；仪表残留投屏区（**安全相关**） | 严格保持「TERM → 等窗口迁回 → 幂等 restore → kill -9」；仪表以 `RESTORE_OK` 为唯一成功判据 |
| R-04 | 裁切页运行中截图 | 用户在投屏时点「框选」 | `screencap` 抢 SF，可能掉 1–2 帧 | 仅点击时截一次；截图期间不轮询状态 |
| R-05 | 应用图标解码进主线程 | UI-01 直接用 `getApplicationIcon` 批量取 | 列表打开卡顿、冷启动变慢 | 后台线程 + 内存缓存 + 懒加载 |
| R-06 | 新增 Activity / assets 改动安装流程 | UI-01 新增页面、UI-03 新增底图 | 覆盖安装失败，或装上了还是旧版（历史上版本号脱节过） | `versionCode` 必须 +1；装完比对 APK md5 与 dex md5（`APK控制器-v0.2.md` §11 的方法） |
| R-07 | 改了 `assets/killvds.sh` 但忘了同步 `tools/remote/killvds.sh` | 维护期两边漂移 | APK 与脚本行为不一致，排查时互相误导 | 以 `tools/remote/` 为源，构建时覆盖（现状已是 `cp`，保持） |
| R-08 | 权限/常驻提示 | UX-10 若加通知 | 需要 `POST_NOTIFICATIONS`，manifest 变更 | 默认不加；要加就单独一批 |

**明确不会碰的**：VdSend 的 LZ4、icrecv 的 dec/draw/flush、单槽队列背压、`compose` 参数顺序、5560 协议。
